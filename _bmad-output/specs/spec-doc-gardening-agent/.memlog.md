- (decision) Why: stale implementation and architecture documentation can cause incorrect implementation or deployment; the system must keep key claims aligned with active IaC code and production reality.
- (capability) CAP-1 — Audit key statements in implementation and architecture documentation against evidence from active IaC code and read-only production observations; success: each audited claim has a traceable three-way evidence set or is explicitly escalated.
- (capability) CAP-2 — Apply an evidence gate that distinguishes consistent state, document drift, production drift, and unresolved evidence; success: only document drift backed by complete evidence becomes eligible for automatic repair.
- (capability) CAP-3 — Repair one independently verifiable documentation discrepancy and open one reviewable PR; success: the PR changes only the target documentation issue, preserves local structure and terminology, states rationale and sources, and reports post-change validation.
- (capability) CAP-4 — Escalate cases requiring human judgment without changing documentation; success: incomplete or conflicting evidence, unclear management boundaries, uncertain active-code status, and persistent unreachability produce a traceable escalation instead of a repair.
- (constraint) The evidence gate is non-negotiable: no automatic documentation change or PR unless the evidence loop is complete.
- (constraint) Within explicit IaC management scope, active code is normative; a production mismatch is production drift and does not justify rewriting documentation to match drift.
- (constraint) When code has an explicit management relationship, it overrides conflicting design documentation; when code does not manage a component, production state is authoritative only if the unmanaged boundary is established.
- (constraint) A component absent from both explicit code management and documented scope must be escalated; the agent must not infer its management boundary.
- (constraint) Production observation must be read-only, non-disruptive, and recorded; services are checked for accessibility, while VM, container, and physical infrastructure are checked for reachability and declared-resource agreement.
- (constraint) Failed availability checks must be repeated at different times; persistent failure triggers escalation and must not be treated as proof of deprecation.
- (constraint) Every audit record states what changed, why, sources consulted, validation performed, and validation result.
- (constraint) Every automatic PR addresses one discrepancy, is logically complete, follows the target document's format, and carries the complete evidence record.
- (decision) V1 prioritizes implementation and architecture documentation and may modify documentation and open PRs; it does not automatically merge them.
- (decision) Non-goals: modify IaC/application code or production state, repair production drift, infer undocumented management boundaries, declare deprecation from availability failure alone, auto-merge PRs, or garden other documentation classes in V1.

- (decision by user) Q1 answered — a component counts as actively IaC-managed only when repository code (role/playbook) exists AND the target host appears in the current inventory (Terraform dynamic inventory or bare_metal/hosts.yml). Code alone is not enough: that is the residual-obsolete-code failure mode the question was about. Both halves are decidable from a checkout plus Terraform state, so no credential is required to establish management scope.
- (decision by user) Q2 answered — retry policy is tiered by target, not uniform. Always-on targets: 3 attempts across at least 24 hours. Targets with a known periodic availability window: at least 2 full cycles. The T7910 cold-backup host wakes by WOL once a week, so its window is about 15 days; a uniform 72-hour policy would treat its normal state as a failure and emit noise every week.
- (decision by user) Q3 answered — V1 key claims are scalars that bind to a deterministic oracle: ports, image tags and versions, file paths, resource specifications, hostnames and IPs. Same shape as the existing Phase 1 claim set, so it extends rather than replaces it. Topology and dependency statements, and operational procedure steps, are out of V1.
- (decision by user) Q4 answered — V1 authorizes exactly one runtime interface: credential-free network probing (TCP reachability and HTTP health checks). No NetBox, Proxmox, HCP or Terraform-state access. The doc-gardening tooling holds no production credential in V1.
- (constraint) Management scope is established from the checkout and Terraform state alone; a component with code but no inventory entry, or an inventory entry with no code, is unresolved and escalates rather than being treated as managed.
- (constraint) A retry schedule must be chosen from the target's availability tier before probing begins; applying the always-on tier to a target with a known periodic window is itself a policy violation, not merely a noisy result.
- (constraint) V1 audits only scalar claims that bind to a deterministic oracle; a statement with no such oracle is out of V1 scope and must not be proposed for repair even when a model is confident about it.
- (constraint) V1 runtime observation is limited to credential-free TCP reachability and HTTP health checks; any interface requiring a token, key or password is out of V1 and needs a new decision before use.
- (decision) The four answers are recorded in observation-policy.md, a new spec-authored companion, because the tier table and the key-claim catalogue each need more than one kernel-shape line; SPEC.md cites it from Constraints.
