# 员工远程 Claude Code 工作环境：第一阶段 / Employee workspace — phase one

本文件与 companions 为本任务的现行契约；sources 是历史输入。2026-10-21已吸收员工sudo、受管跳板机及用户选择1A／2A：正常公网开发出站，OAuth流程验收，不承诺杜绝全部员工自建中继或sudo替换令牌。

## Why

5–10 位在中国出差的员工需要稳定完成 Claude Code 代码任务，环境位于澳洲家庭服务器。员工在现有 Cloudflare 网页终端和 cloudflared 原生 SSH 均反馈高延迟；澳洲侧 VM 已验证正常。本阶段以真实项目和所在地工作网络检验个人受控终端环境。

## Capabilities

- **CAP-1**
  - **intent:** 员工在本人持久VM拥有sudo，自主管理工具与依赖，完成代码工作。
  - **success:** 通过受管入口进入本人VM，自行安装工具、准备依赖、修改、检查／测试及Git／SFTP交付；个人项目与配置按A-1保留。
- **CAP-2**
  - **intent:** 员工在目标终端环境使用自己的 Claude 订阅身份。
  - **success:** 核实订阅资格后，独立 OAuth 令牌认证并完成可确认本人订阅的请求；凭据泄漏检查覆盖约束列明的材料，且不输出秘密值。
- **CAP-3**
  - **intent:** 员工仅访问本人资源，与其他员工及管理网络隔离。
  - **success:** 受管入口仅允许本人资源，入口内置转发被拒绝，不能绕过入口直接连接VM。VM外规则拒绝矩阵中的受保护目标，修改客户机路由或伪装地址不扩大权限；覆盖二层、IPv4／IPv6、公网回流及实际部署的跨节点路径。不承诺识别员工通过获准数据通道自建的全部中继。
- **CAP-4**
  - **intent:** 公司提供环境的Claude运行及授权使用澳洲VM，受管网络经澳洲出口。
  - **success:** 员工本人按Q-2在澳洲VM完成浏览器登录／同意，核对实际账号、认证来源与请求出口；受管网络路径及入口拒绝转发有实测证据。不建立防sudo替换凭据机制，也不承诺识别全部自建加密代理／终端中继。
- **CAP-5**
  - **intent:** 员工从实际所在地稳定工作，并逐步覆盖 5–10 人。
  - **success:** 试用及扩展后的实际并发下完成真实任务，员工与负责人确认日常可用；每位新员工上线前完成 verification.md 的最低检查。
- **CAP-6**
  - **intent:** 管理员按设备和员工分配、撤销环境访问。
  - **success:** 设备撤销使其公司受管接入身份／会话失效，范围见access；员工停用撤销全部公司身份／规则／SSH授权，并从VM外断网或停机、终止既有通道且保盘，按Q-6处理数据及凭据。

## Constraints

- 第一阶段纯终端、每人独立个人 OAuth；一次性图形授权通道也未默认获准。完成 Claude 登录／同意的浏览器会话及 Claude 运行环境都必须在澳洲 VM 内，相关请求经澳洲出口；最小操作入口待 Q-2。
- 员工保留本人VM的sudo并自主管理工具与依赖，公司提供基础Claude Code。受管入口与受保护网络隔离在员工不可修改的VM外执行；普通公网开发连接允许，经公司澳洲路由出站。
- 公司接入自建维护，独立于个人Tailscale；已选择受管SSH跳板机，以固定设备身份到VM映射建立两段SSH并支持SFTP，入口无员工自由shell／sudo，禁内置转发及隧道。其员工接入服务、协议必需入口与明确基础服务按例外放行，管理面仍拒绝。
- 隔离按受保护目标及最终路径执行，包含家庭／个人Tailscale／PVE管理网、家庭网关及所选公司接入设施本机服务和家庭公网回流；DNS例外、IPv6处理及维护来源明示于设计。
- 令牌和私钥在分配后配置，不进入Git、Terraform输入/state、Cloud-Init、模板、命令历史、普通日志或交给管理员的排错材料；浏览器登录态／会话也是个人凭据。含凭据快照／备份的许可、访问与留存由Q-6在首次配置凭据前确定，不默认禁止所有备份；系统部署凭据沿用采用的Vault架构。
- 保留既有WAN、DNS/DHCP、qnetd、个人代理和管理通道；新地址、VMID及网络配置先对账，沿用Terraform／Ansible职责分工，见brownfield.md。
- 受管SSH入口方向已定；外层接入协议、VM参数、Linux及具体网络部署保留候选状态；不虚设性能阈值。澳洲侧完成基准不重复列为待办，接入效果以实际任务和反馈判定。

## Non-goals

- 第一阶段验收完成后，按第二阶段浏览器→第三阶段IDE的顺序推进；高层后续目标见phased-roadmap.md，不增加本阶段能力或验收项。常规浏览器、IDE分别留到第二、第三阶段；第一阶段若需图形授权入口，须另经用户确认。不采购Team或切API计费。
- 不技术控制员工在公司环境外独立使用本人账号／令牌，不承诺令牌不可复制或防sudo主动替换。允许正常公网开发连接，不承诺杜绝所有员工自建加密代理及通过终端等数据通道的中继；该范围不削弱受管入口转发拒绝、VM外受保护目标隔离或员工外部停用。
- 不建设内部共享服务、集中监控／日志、认证门户、令牌代发／自动续期；不增加独立恢复、会话保活、HA、多协议网关、云中继或备用线。

## Success signal

员工从中国实际工作网络进入本人环境，以本人订阅完成代码任务及交付；受管入口、网络隔离、实际授权与模型请求路径、凭据和访问生命周期均有通过证据。扩展后的实际并发仍获员工与负责人确认可用；静态配置生成不替代实测。

## Assumptions

- **A-1:** 个人VM按持久工作空间理解，保留项目与配置，不推导备份或恢复SLA。
- **A-2:** 用户所说上行“50mb”按50Mbps理解；未测速，不保证跨境质量或容量。

## Open Questions

- **Q-1:** 哪条实测后的自建接入成为正式入口？WireGuard未测，WARP／VLESS只作对照；转正式托管入口须先明确与自建要求的兼容性或变更范围。
- **Q-2:** 授权浏览器须在澳洲VM；先核实终端浏览器能否完成真实流程。若只能用图形方式，是否允许一次性图形授权入口须用户决定。以原生交互订阅OAuth登录为优先实现候选，验证实际账号／来源／出口；不增加防sudo替换或密码学来源绑定组件。凭据副本按Q-6管理。
- **Q-3:** 每位试用员工的订阅资格、客户端系统、真实项目、Linux适用性及实际并发是什么，资源如何按负载确定？
- **Q-4:** 核实PVE后端／启用层级、网桥／VLAN／交换能力及已有试用VM后，如何确定VM外隔离、DNS、地址、维护来源及正常公网开发出站的具体规则？
- **Q-5:** 家庭入站／NAT回流、公网地址／域名，以及现有公司Access应用、连接器位置和路由是什么，正式上线时如何纳管或退役？
- **Q-6:** 个人凭据（含浏览器登录态／会话）及快照／备份副本允许如何保存、谁可接触、以何授权处理？首次配置凭据前明确相关备份许可与访问／留存，停用后再按授权处理保留盘、交付及删除。

已解决的A-3、Q-7保留历史编号。A-4已被用户选择2A的流程验收取代；A-5由全面防绕行推导的强制先行试测限制随1A撤销，线路测量仍可作参考。Q-8的边界取舍已由sudo、跳板机及1A／2A决定，具体配置和验收仍按Q-2／Q-4及verification.md执行。历史编号不复用。
