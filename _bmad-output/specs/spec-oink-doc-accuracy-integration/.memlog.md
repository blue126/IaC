- (direction) Source research.md is fully absorbed; this focused Phase 1 uses only a small, closed set of code-backed claims and is intentionally separate from the broader doc-gardening-agent spec.
- (decision) Why: stale IaC documentation can mislead operators and agents, while the existing Notion synchronizer currently reads Vault or Terraform secret material, writes credentials and tokens to Notion properties/notes, and prints password prefixes in dry-run output; the sensitive-data boundary must be corrected before adding documentation automation.
- (capability) CAP-1 — Make the retained Notion inventory synchronization path incapable of exporting or logging Vault/Terraform credential values; success: mocked runs seeded with unique secret sentinels prove that outbound Notion properties and stdout/stderr contain none, while non-sensitive inventory metadata remains synchronizable.
- (capability) CAP-2 — Evaluate the closed Phase 1 registry of four documentation claims against their declared repository files using deterministic parsers and exact value comparisons; success: fixtures covering match, mismatch, missing source, and ambiguous/missing document locator yield the specified status and evidence for every registered claim.
- (capability) CAP-3 — Produce a non-sensitive, machine-readable drift report and a human-readable summary that bind each result to document locator, oracle path/key, expected and observed non-secret values, and source revision or content digest; success: a repository-only run reports all four registered claims without network or production credentials and returns a non-zero result on contradiction or indeterminate evidence.
- (constraint) CAP-1 is a blocking prerequisite: no claim report, OINK-facing manifest, docs build job, test fixture, log, or Notion payload may contain Vault values, Terraform secret values, passwords, API tokens, integration tokens, or derivatives such as masked prefixes.
- (constraint) The Phase 1 registry is closed to four scalar claims: netbox_port, netbox_image, llm_server_engine_version, and llm_server_webui_port; each maps one stable document locator to one checked-in Ansible defaults key and excludes any credential-bearing field.
- (constraint) Oracle evaluation is repository-only and deterministic: parse the exact Markdown locator and YAML scalar, compare normalized scalar values, retain evidence identifiers, and mark missing, ambiguous, or unparsable evidence indeterminate rather than guessing.
- (constraint) OINK/Hugo and GitHub Pages remain unprivileged presentation and verification planes: they may consume only the generated non-sensitive report or manifest and must not invoke the detector against runtime systems or receive Notion, Vault, Terraform, HCP, NetBox, Proxmox, or ESXi credentials.
- (constraint) The detector must use the checked-out revision or file digest for provenance and must not use wall-clock freshness as evidence of correctness.
- (decision) The claim registry is a spec-authored companion because the per-claim document locators, oracle keys, normalization, and expected fixture behavior are load-bearing catalog data.
- (decision) A security-boundary companion is spec-authored because the Notion remediation acceptance contract and prohibited data classes need more detail than one kernel constraint.
- (direction) No runtime collector, AI claim extraction, AI-generated documentation edit, automatic documentation edit, PR creation, or automatic merge is authorized in this phase.
- (assumption) The existing sync-to-notion.py path remains a supported inventory integration after remediation; if it is to be retired instead, the replacement or removal decision must supersede CAP-1 before implementation.
- (question) Must the Phase 1 detector execute only as a local/CI check, or should its non-sensitive report also be rendered by the OINK site after the security gate passes?
