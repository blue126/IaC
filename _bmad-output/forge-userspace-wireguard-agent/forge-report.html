remotecc 员工客户端

起点：用免 sudo/UAC 的用户态 WireGuard 代理替代系统隧道。
终点：特权守护进程 + TUI，安装时授权一次，之后日常免提权。最初的“完全免 sudo”形态已被否决，演化后的想法锻成。

结论

真正的目标不是“免 sudo”，而是让员工安装和日常使用都尽量容易。一旦安装时授权一次可以接受，用户态代理的核心优势就缩水了，它要付出的代价却还在：127.0.0.1 转发、改 nginx、证书名称不匹配、mosh 整段端口。因此改用一次授权的特权守护进程，访问方式完全不变，再加一个 TUI 作为每天的入口。

1 · 首次送达brew install / curl / PowerShell 一行命令
2 · 唯一一次提权sudo remotecc install 设备包
3 · 每天remotecc，回车进入工作区

锁定的决定

  • 形态守护进程内嵌 wireguard-go，自己管理网卡和 /32 路由，不依赖 wg-quick、wireguard-tools 或 bash 4；10.234.0.2、desktop_url、nginx、ssh 配置都不变。
  • 仓库新建公开仓库 remotecc-client 放客户端，另建 homebrew-tap；workspace-onboarding 过渡期继续负责接入新员工；私有 remotecc 不变，两边靠设备包 schema、Releases 格式和验签公钥衔接。
  • 平台第一期 Mac、Linux、Windows 一起做，最后只保留一条接入路径。
  • 安装不再需要 bootstrap。remotecc 负责校验、安装和 verify；README 只告诉 Agent 运行哪几步。分发以 Homebrew tap 为主，curl 兜底。
  • 提权防线只运行 root 拥有的副本；控制通道只认安装时记录的员工身份，只接受白名单命令，客户端不能传路径或二进制；私钥只放在 root 目录。
  • 重新安装换发设备包或换账号，都按重新安装处理，再授权一次。
  • TUI同一屏看状态、换线路、确认更新、打开 VM 桌面；mosh <id>-vm 仍可直接用。
  • 更新默认自动检查，安装前由员工确认，也可以关掉；签名私钥放在 GitHub Actions secret，公钥写死在二进制里；本地保留上一个版本，自检失败就自动退回。
  • Windows先不签名上线：PowerShell 分发不带网络来源标记，SmartScreen 一般不弹；install 检测到 Smart App Control 开着时提示员工关掉。同时把客户端开源，申请 SignPath Foundation 的免费签名，批下来后切换。
  • 迁移签发新设备包（新密钥）→ install 拆掉旧隧道、装上新隧道、运行 verify → 通过后在 Hub 撤销旧密钥。

否决的方案

  • KILLED完全免 sudo 的用户态代理：一次授权可以接受之后，它为免授权要改的访问方式不值得。原型证明它做得到，但不是该做。
  • KILLEDDocker：在 Mac 上和用户态代理有同样的访问方式代价，还要额外装 Docker Desktop 并常驻一个虚拟机。
  • 否决用 Homebrew 负责更新（要员工手动 upgrade）；静默自动更新；在 /me 页面下载未签名的 CLI；付费 Windows 签名（云签名按月订阅，个人资格可能已暂停；传统证书每年几百美元，都太贵）；沿用旧私钥迁移；让员工手动卸载旧隧道。

仍未解决的风险

  • 信任根GitHub 或 CI 被攻破后，攻击者可以很快把恶意版本推给所有员工。缓解办法是受保护 Environment 加人工审批，并且只对受保护的 tag 签名。这需要单独授权。
  • 前置依赖没装 Homebrew 的 Mac，以及 Linux 和 Windows 上的 mosh，仍然要提权或额外安装。
  • 环境差异测试覆盖不到各种员工环境。本地自动回退只兜住了“更新后起不来”这一种情况。
  • SignPath条款要求项目先以待签名的形式发布过，可执行程序还要有“可验证的声誉”，审核也不一定批，所以不签名的时期可能会很长；批下来后显示的发布者是 SignPath Foundation。在那之前，开着 Smart App Control 的员工必须一直关着它。
