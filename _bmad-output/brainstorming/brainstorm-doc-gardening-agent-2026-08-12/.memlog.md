goal: 讨论并收敛一个能发现文档与真实代码行为偏差、产出小型修复 PR 的可实施方案

- (technique) started Role Playing
- (idea) 目标：发现并修正文档描述与代码实现不一致的问题。
- (insight) 主要风险：agent 可能误改文档，或遗漏应同步的信息。
- (decision) 一致性的核心验收标准：文档内容、代码实现、生产环境实际状态三者相互吻合。
- (decision) 允许 agent 使用任何不会影响或破坏生产环境的只读观察方式。
- (decision) 每次生产核验必须留下可追溯的工作记录。
- (decision) 工作记录至少包含：做了哪些更改、为什么更改、查阅了哪些资料、改后是否执行验证、验证结果是什么。
- (decision) 首要扫描范围：实施文档和架构文档，因为其过时最容易导致错误实现或错误部署。
- (technique) started First Principles Thinking
- (decision) 不可再简化的目标：实施文档和架构文档中的关键陈述必须与现实保持一致。
- (decision) 真相优先级：在 IaC 覆盖范围内，代码应代表现实；代码与生产不一致属于生产漂移。代码未覆盖或未管理的组件属于例外，其生产状态可作为现实依据。
- (decision) IaC 管理边界由设计文档声明；设计文档未提及的生产组件必须升级给人判断，agent 不自行归类。
- (decision) 若设计文档与代码或生产证据冲突，只要代码存在明确管理关系，仍以代码为准；文档应被视为待修正对象。
- (question) 待决：需要什么代码证据，才能证明某组件仍由 IaC 有效管理，而非仅存在相关但已废弃的代码？
- (technique) started Reverse Brainstorming
- (insight) 废弃或失效代码的可观察信号：其描述与生产网络状态存在大量甚至完全不一致。
- (decision) 有效 IaC 的运行时证据：服务应可访问；VM、容器和物理机应可达，且实际资源配置与代码声明一致。
- (decision) 可达性探测失败必须在不同时段重试多次；持续不可达时升级给人判断，agent 不得据此自行判定代码或文档废弃。
- (insight) 不可审阅 PR 的特征：一次包含过多更改、内容逻辑不通顺、格式不一致、未提供更改原因和证据。
- (decision) doc-gardening PR 硬规则：单一问题；逻辑完整并区分设计目标、代码声明、生产现状；格式遵循目标文档现有规范；证据闭环，证据不足只升级人工判断而不自动修改。
- (technique) started convergence with Affinity Clustering
- (decision) 不可妥协的核心：只有形成完整证据闭环，才允许 agent 自动修改文档并开启单一问题 PR。
- (insight) 证据闭环应实现为状态门禁而非仅作 PR 模板：证据完整进入自动修复与 PR 路径；证据不完整进入人工升级路径，禁止修改文档。
