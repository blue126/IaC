# Doc-Gardening Agent Intent

## Intent

在 IaC 仓库中引入 recurring doc-gardening agent，持续发现并修正实施文档、架构文档中的关键陈述与代码实现、生产环境实际状态之间的偏差。首版只在证据形成完整闭环时自动修改文档，并为单一问题创建小型、可审阅的 PR；证据不足时只升级人工判断。

## Core Evidence Gate

自动修复路径的不可妥协条件是完整 evidence loop：

- 明确待核验的文档关键陈述；
- 确认相关组件是否存在明确的 IaC 管理关系；
- 通过不会影响或破坏生产环境的只读观察，核对服务或资源的实际状态；
- 对服务验证可访问性，对 VM、容器和物理机验证可达性，并核对实际资源配置与代码声明是否一致；
- 保留可追溯工作记录，至少说明改了什么、为何修改、查阅了哪些资料、是否执行改后验证及验证结果。

门禁是执行状态机，而非 PR 模板提示：证据完整才进入文档修改与 PR 路径；证据不完整则进入人工升级路径，禁止修改文档。

## Truth Priority

1. 在 IaC 覆盖范围内，代码代表应有现实；代码与生产状态不一致属于 production drift。
2. 当代码存在明确管理关系时，即使设计文档与代码或生产证据冲突，仍以代码为准，文档是待修正对象。
3. 对代码未覆盖或未管理的组件，以生产状态作为现实依据。
4. IaC 管理边界由设计文档声明；设计文档未提及的生产组件不得由 agent 自行归类，必须升级人工判断。

## V1 Scope and Behavior

- 优先扫描实施文档和架构文档。
- 聚焦文档关键陈述与代码声明、生产现状之间的不一致。
- 生产核验只允许使用不影响或破坏生产环境的只读观察方式。
- 可达性探测失败时，必须在不同时段重试多次；持续不可达只触发人工升级，不得据此判定代码或文档已废弃。
- 只有通过 evidence gate 的单一问题可以自动修正文档并创建 PR。

## Human Escalation Boundary

以下情况禁止自动修改并必须升级人工判断：

- 无法形成完整证据闭环；
- 设计文档未声明生产组件的 IaC 管理边界；
- 无法确认相关代码仍有效管理组件，而非仅为相关但已废弃的代码；
- 多次、跨时段探测后资源或服务仍不可达。

## PR Hard Rules

每个 doc-gardening PR 必须：

- 只处理一个问题；
- 内容逻辑完整，并明确区分 design target、code declaration 与 production state；
- 遵循目标文档现有格式；
- 说明修改原因并提供可追溯证据；
- 包含改后验证及其结果；
- 在证据不足时不创建自动修复 PR。

## Unresolved Question

- 哪些代码证据足以证明组件仍由 IaC 有效管理，而不是仅存在相关但已废弃的代码？该判定标准必须在允许自动修复前明确。
