# 员工远程开发环境：三阶段路线图

日期：2026-10-21（Australia/Sydney）
状态：补齐后续阶段的方案草案；阶段顺序与共同目标已由用户确定，具体产品、协议及新增能力均保留候选状态。本文件不是部署记录或正式 SPEC。

## 1. 总体目标与阶段关系

为 5–10 位在中国出差的员工提供澳洲服务器上的个人开发环境，逐步达到接近本地开发的使用体验。用户已接受远程桌面方向，明确顺序为先 Claude Code、再浏览器、再 IDE。

| 阶段 | 员工得到的能力 | 主要运行位置 | 本阶段交付判断 |
|---|---|---|---|
| 第一阶段：终端 | 使用本人 Claude OAuth 完成代码任务、项目检查与交付 | 个人澳洲 VM 内的终端和项目环境 | 接入日常可用、任务完成、身份／隔离／出口验证通过 |
| 第二阶段：浏览器 | 在个人环境内使用网页、完成所需登录，并查看项目网页效果 | 个人澳洲 VM 内的浏览器，通过远程图形入口操作 | 浏览器工作流可用、数据按人持久保存、新入口不扩大他人访问权限 |
| 第三阶段：IDE | 编辑、查看差异、运行／调试项目，并在 IDE 中配合 Claude Code | 同一澳洲 VM 内的 IDE、Claude 与项目工具 | 完成一个真实的 IDE + Claude 工作流，插件和授权仍符合出口及隔离要求 |

第一阶段详见 [phase-one-proposal.md](phase-one-proposal.md)。本路线图补充后续方向，不把浏览器与 IDE 的日常能力提前并入第一阶段，也不把第一阶段候选参数当作已选定的长期架构。

所有阶段共用的边界：个人持久工作环境、员工间隔离、公司接入自建维护且独立于个人 Tailscale、Claude 的运行和授权请求来自澳洲 VM／澳洲出口。接入协议及线路继续依据实际测试选择；扩展阶段不能假设 WireGuard 已验证稳定。

## 2. 第二阶段：个人 VM 内的浏览器

### 目标和使用流程

“加入浏览器”指在澳洲 VM 内运行浏览器应用，不是第一阶段试过的网页 SSH 终端。员工电脑承担远程显示与输入，网页加载、下载和网站请求发生在澳洲 VM。

候选流程：连接公司接入网络 → 打开本人远程图形会话 → 使用 VM 内浏览器 → 查看网页或同一 VM 上运行的项目 → 回到终端继续开发。

网页用途按员工实际需要确定。候选包括阅读开发文档、必要的网站登录／授权、使用 Claude 网页以及本地 Web 项目预览；不能将这些举例全部当成已确认的必需能力。自动化操作浏览器、Playwright／MCP 集成目前没有被用户要求。

### 建议实现

优先评估在原有个人 VM 上增补轻量桌面和浏览器，保留原项目、账号及配置。每人独立操作系统用户与浏览器配置目录，网站登录、书签、下载文件等按人持久保存；不使用共享浏览器会话，也不在克隆模板中预置个人 Cookie 或令牌。

图形入口先比较经公司网络访问本人 VM 的原生远程桌面。xrdp／RDP 是候选之一，不在本文件确定协议、端口放行或安装操作。[xrdp 官方项目](https://github.com/neutrinolabs/xrdp)

仓库已有 RustDesk 的 VM102／192.168.1.102 声明及 server role，可作为现有能力的评估对象。现有 role 配置允许直连并可回退中继；这不证明服务此刻可用、适合员工隔离或已获准用于公司网络。若比较 RustDesk，必须检查实际直连／中继路径、身份及本人 VM 映射，不能把员工自动加入既有个人服务。相关源码为 `terraform/proxmox/rustdesk.tf` 和 `ansible/roles/rustdesk/`。[RustDesk 官方自建说明](https://rustdesk.com/docs/en/self-host/)

暂不因加入浏览器就新增公共桌面门户。若原生图形入口不适合实际员工，再单独评估浏览器中的远程显示；即使显示界面在员工本地浏览器中，Claude 网站本身仍在澳洲 VM 内打开。

### 网络、认证与权限

图形入口只允许本人设备访问本人会话／VM。员工之间、家庭／个人网络与基础设施管理面的隔离继续生效；不能为了桌面访问开放整个员工子网、PVE 控制台或其他员工服务。

Claude 网站登录／同意与模型请求都在澳洲 VM 内发生。第一阶段个人 OAuth 仍可供 CLI 使用；网页会话单独登录，不假定 CLI 令牌会自动建立浏览器会话。第二阶段可提供以后的令牌替换操作环境，但不能反过来把第一阶段缺失的首次授权条件视为已完成。

剪贴板、文件传输、浏览器扩展和输入法需要在试用时明确实际需求；特别是中英文输入、复制代码、下载文件等基本操作。其允许范围沿用正式规格认可的权限边界，不默认开放任意跨端设备重定向、额外代理或不受管入口。

### 资源与验收

先在一个员工环境试用，再扩大到两人及实际并发。可从单屏 1080p 的候选测试条件观察图形体验；该分辨率不是已确认要求。桌面与浏览器会增加资源和网络占用，应测量现有 50 Mbps 家庭上行的实际并发表现，不能从“终端可用”直接推定桌面也可用。

远程桌面带宽随应用、画面变化和分辨率而变，实际会话最能说明容量需求；此处引用 RDP 资料作为评估原则，不据此声称所有协议的带宽相同。[微软 RDP 带宽说明](https://learn.microsoft.com/en-us/azure/virtual-desktop/rdp-bandwidth)

第二阶段候选验收：

- 员工从实际工作网络打开本人图形会话，在 VM 浏览器中完成一种真实网页工作流。
- 所需中英文输入、复制粘贴及文件操作可用，数据留在本人持久目录；另一员工无法读取或连接其会话。
- 如涉及 Claude 网站或授权，确认浏览器进程、会话和相关请求都在澳洲 VM／出口。
- 第一阶段终端、项目和 OAuth 仍可正常工作，新增入口符合已认可的网络与权限边界。
- 实际并发下员工确认图形交互可用于日常工作；必要时调整画质或资源，再决定是否扩大使用。

## 3. 第三阶段：VM 内的 IDE 与 Claude Code

### 目标和使用流程

在第二阶段的个人图形环境上加入 IDE。员工通过远程桌面打开项目，IDE、Claude、语言工具、测试、调试器和浏览器都在自己的澳洲 VM 内运行，继续使用原来的项目目录，避免维护一份本地、一份远端的双份工作区。

候选工作流：打开项目 → 在 IDE 中描述代码任务／选中文件内容 → Claude 修改 → 查看差异并人工调整 → 运行测试或调试 → 用第二阶段浏览器验证页面 → 提交／交付结果。

VS Code 可作为试用候选；JetBrains 等由实际技术栈、员工习惯与许可条件决定，不预装或承诺所有 IDE。用户目前确认的是“配合 IDE”，尚未指定产品。[Claude Code 的 VS Code 集成](https://code.claude.com/docs/en/vs-code)、[JetBrains 集成](https://code.claude.com/docs/en/jetbrains)

### 两种集成深度

| 候选方式 | 员工操作 | 需要验证的内容 |
|---|---|---|
| IDE 内置终端 + 已有 Claude CLI | 在 VM 内 IDE 终端使用已有个人令牌和 CLI，并查看项目与差异 | 环境变量继承、工作目录、身份和既有工作流可用 |
| IDE 原生 Claude 插件／面板 | 在 IDE 中引用文件、查看差异并与 Claude 交互 | 插件具体版本、其 Claude 进程位置、个人令牌或 VM 内登录兼容性、请求出口与权限 |

第一种可作为集成起点；原生面板作为进一步体验，需单独验证。VS Code 扩展自带用于面板的 CLI，内置终端运行的独立 CLI 并非同一个安装来源。因此不能因为第一阶段 `claude` 可用，就宣称插件认证及运行也已经可用；如需浏览器登录，使用第二阶段的 VM 内浏览器，不把链接在员工本地打开。[官方 CLI／扩展区别](https://code.claude.com/docs/en/vs-code#vs-code-extension-vs-claude-code-cli)

### 网络、账号与开发工具

沿用公司接入和本人图形入口。IDE 内置终端、调试器、插件及浏览器不得因新增功能获得对其他员工资源或基础设施管理面的访问。个人 OAuth 保留，不把开通 Team、切换 API 计费或新建模型网关作为第三阶段前置条件。

所有 Claude 相关运行组件、插件认证及相关请求仍在澳洲 VM 内。默认展开的方案是 VM 内完整 IDE；“本地 IDE + Remote SSH”仍是可评估的替代，不作为默认交付。若日后考虑替代方式，应先逐项核实插件运行位置、登录浏览器及请求路径，不能假定 Remote SSH 自动将所有组件搬到 VM。

项目依赖、语言插件、调试目标按实际项目增加，权限由正式规格决定，不预先承诺无限制安装或本地设备转发。项目 Web 服务优先让同一 VM 内的浏览器访问；若确需员工电脑访问项目端口，应作为明确例外设计本人限定访问，不将开发端口直接发布到公网。

### 验收

第三阶段候选验收：

- 在 VM 内 IDE 打开员工真实项目，完成修改、差异查看、检查／测试和交付。
- 通过选定的终端或插件集成，让 Claude 在正确项目上工作，并验证是本人订阅身份。
- 所需诊断、调试与页面验证可用；不将所有 IDE 功能或所有技术栈当成已验证。
- IDE、Claude 插件及授权浏览器的运行与请求路径符合澳洲 VM／出口要求。
- 新增终端、插件、调试及文件功能未突破已认可的隔离与权限边界，员工间测试仍通过。
- 实际多人工作负载下，CPU、内存、磁盘和远程图形体验可用；按测量调整个人配置。

## 4. 跨阶段依赖与实施原则

| 从上一阶段保留 | 下一阶段新增并验证 |
|---|---|
| 第一阶段的个人项目、身份、受管接入、隔离和澳洲出口 | 第二阶段的图形入口、浏览器配置持久化和图形并发体验 |
| 第二阶段的本人桌面、浏览器和项目目录 | 第三阶段的 IDE、Claude 集成、语言工具、调试与实际代码工作流 |

阶段切换优先增量配置，避免为了加浏览器或 IDE 重建并清空个人 VM。确需更换系统时，先明确项目、配置和凭据的保留／迁移安排；本路线图不授权覆盖磁盘。

前面用户排除的额外恢复、会话保活、HA、集中监控／日志和内部共享服务，不因阶段增加自动变成必做事项。未来 Team 采购、公司共享服务都是独立决定，不在三阶段之外虚构一个必经第四阶段。

员工权限及受控出口如何落实，承接经用户确认的正式规格；早期管理员权限安排不能自动视为所有后续阶段的最终授权。新增浏览器、桌面控制和 IDE 代码执行能力若与既定边界冲突，应先在相应阶段的规格中明确取舍，不能用工具名称代替控制实现。

## 6. 仍需确认的后续阶段选择

- 第二阶段浏览器的主要用途及所需网站；是否包含 Claude 网页和项目页面预览。
- 个人 VM 的最终操作系统及图形桌面、远程显示协议；现有 RustDesk 是否适合作为候选比较。
- 图形会话的输入法、剪贴板、文件传输、分辨率及实际并发需求。
- 第三阶段采用的 IDE、员工实际技术栈、终端集成与原生插件所需深度。
- 各阶段新增入口与代码执行能力如何遵守最终确认的权限和出口边界。

这些条目保留为候选／开放项，不要求现在一次性回答，也不影响先形成完整的三阶段规划输入。
