## 成功经验

### 1. 递进式验证模式

4 个 Story 形成清晰依赖链：Custom Fields → Webhook → VM 创建 → API 验证。每一步验证为下一步打基础，端到端贯穿整个 Epic。**这个模式值得在后续 Epic 中继续沿用。**

### 2. 拥抱约束催生更优方案

Story 1.2 中 `readJSON`（Pipeline Utility Steps 插件）安装失败。团队转向 Generic Webhook Trigger 的原生 `genericVariables` 配置，通过 JSONPath 直接提取环境变量。结果：零额外插件依赖，代码更简洁可靠。

**可复用经验**: 遇到插件/工具障碍时，优先考虑平台原生能力能否解决问题，而不是死磕安装。

### 3. API 性能超预期

Story 1.4 所有查询 < 500ms（目标 < 2s，NFR 要求 < 30s）。Custom Field 过滤（`cf_infrastructure_platform=proxmox`）6 种组合全部正确。NetBox API 设计扎实，为后续 Terraform 集成提供信心。

### 4. 测试脚本的复用价值

`scripts/jenkins/test-webhook-payload.sh` 支持反复模拟 webhook 触发，避免每次手动操作 NetBox UI。在调试 Story 1.2 的 Payload 格式问题时发挥了关键作用。

## 挑战与教训

### 1. 系统性文档基线偏差（最大教训）

**根因**: Story 技术设计基于 NetBox 3.x API 文档编写，但运行环境是 NetBox 4.x (v4.1.11)。

**导致的 3 个关联坑**:

| 坑 | 描述 | 影响 |
|----|------|------|
| Event Rule 架构差异 | 文档写的是在 Webhook 上直接配 `type_create`/`type_update`，但 4.x 需要单独创建 Event Rule，且字段名不同（`object_types` 而非 `content_types`，`event_types` 而非 `type_create`） | 首次创建的 Event Rule 字段为 null，需删除重建 |
| Payload 格式映射 | 文档假设 `event: object_created`，数据在 `$.snapshots.postchange`。实际 4.x 映射为 `event: created`，数据在 `$.data` | Jenkinsfile regexp 不匹配，webhook 被静默丢弃 |
| Webhook API 字段 | 创建 Event Rule 需要 `action_object_type: extras.webhook`，3.x 文档未提及 | API 调用失败 |

**决策**: Will 决定在 Epic 2 开始前做完整的文档 Sanity Check，更新 `architecture.md`、`epics.md` 中所有基于 3.x 的内容。（选项 B — 更新上游文档，而非仅修 Epic 2 Story）

### 2. 静默失败的黑盒问题

NetBox webhook 发送状态显示 "Successfully completed"（HTTP 200），但 Jenkins Generic Webhook Trigger 的 regexp 不匹配，**静默丢弃请求**。没有报错，没有日志。排查只能靠翻 NetBox 源码找到 `WEBHOOK_EVENT_TYPES` 映射。

**可复用经验**: 中间链路必须有可观测性。webhook → Jenkins 这段需要明确的反馈机制，不能只依赖两端分别看状态。

### 3. 中间产物文档未同步更新

Story 1.2 完成总结中写 Payload 路径为 `$.snapshots.postchange`，但最终 commit `d359eb2` 使用的是 `$.data`。完成总结在中间阶段写成后未随最终实现更新。

**可复用经验**: Story 标记 done 时，完成总结必须反映最终实现状态。

### 4. Jenkins 鸡生蛋问题

当 Jenkinsfile 中 GenericTrigger 的 regexp 配置变更后，必须先手动触发一次 build 才能加载新配置。在此之前，真实 webhook 会因为旧的 regexp 不匹配而被忽略。

**可复用经验**: 这是 Jenkins Generic Webhook Trigger 的已知行为，应作为标准部署步骤记录在 checklist 中。

## 关键技术发现（供后续 Epic 参考）

### NetBox 4.x 架构要点

1. **Event Rule 是独立实体** — Webhook 只定义 HTTP 配置（URL、method、headers），事件触发条件在 Event Rule 中定义
2. **Payload event 字段映射** — `WEBHOOK_EVENT_TYPES`: `object_created → "created"`, `object_updated → "updated"`
3. **数据在 `$.data`** — 不是 `$.snapshots.postchange`
4. **Event Rule 必填字段** — `object_types`, `event_types`, `action_type`, `action_object_type`, `action_object_id`

### NetBox Docker 架构

6 个容器: netbox, netbox-worker, netbox-housekeeping, postgres, redis, redis-cache。Worker 通过 RQ queue 处理 webhook 发送。

### Jenkins Generic Webhook Trigger 最佳实践

- 用 `genericVariables` + JSONPath 直接提取变量到 `env.*`，不要用 `readJSON`
- regexp 变更后需手动首次 build
- `printContributedVariables: true` 和 `printPostContent: true` 对调试非常有价值
