## high

1. **位置：AD-8、AD-9、AD-12——`no_expiry` 无法按现有快照契约无歧义执行。**
   问题：AD-8 要求标记优先于任何 `paid_through`，但 AD-12 只允许传输 `employee_id`、`paid_through`、`generation`；AD-9 直接比较日期，并规定快照中缺失的员工不处理。没有规定不到期员工应传空日期、从快照排除，还是采用其他表达，也没有规定空日期如何清除已有 `expired`。
   分歧：执行器可能排除该员工，OCI timer 因而保留旧的到期停用；另一实现可能继续发送原日期，导致不到期员工仍被断开。
   建议修法：固定快照 schema 和投影规则，例如保留全部在册员工，将 `no_expiry` 投影为 `paid_through: null`，并明确 null 必须移除 `expired`；同时定义取消标记及缺失员工的行为。

2. **位置：AD-6、AD-8、上线迁移——遗漏 ticket R14 的存量初始化要求。**
   问题：spine 只规定新开户的日期和 `no_expiry` 行为，没有承接“其余现有员工初始化为上线当月月底”，也没有承接 ticket Done when 中对 `pilot`、`control` 的指定豁免。
   分歧：一个单元可能把缺失日期解释为永久不到期，另一个单元可能补日期或拒绝处理；定时任务也可能在初始化完成前启用。
   建议修法：增加统一迁移规则：指定豁免对象、其他存量员工的初始化月份、幂等处理和完成校验，并将初始化及首份快照成功设为到期任务启用前置；保留 ticket 要求的原设备身份。

3. **位置：AD-2、AD-16——续费开机与人工停机缺少可区分的事实。**
   问题：AD-16 同时要求“已续费则开机”和“不会把人工关闭的 VM 开回来”，但事实所有权表只提供 PVE 当前电源状态，没有定义能够证明停机由到期任务造成的依据。
   分歧：按“未到期且已关机”判断会撤销人工停机；只观察日期变化则可能在执行器重启、重试或控制台续期后漏开机。
   建议修法：定义由执行器持有的到期关机操作凭据及其持久化、重放和消费规则，明确只有符合该凭据的续费恢复可以自动开机。该凭据应是操作事实，而非另存生命周期状态。

4. **位置：AD-12、AD-16、Consistency Conventions——执行契约不足以兑现 ticket R5、R6、R19 的时限。**
   问题：每 5 分钟启动一次任务，先进行最长 60 秒的 HAPI 推送，再关机，即使没有其他故障，也可能超过到期后 5 分钟；“下一次成功、通常 5 分钟内”进一步放宽了 ticket 的硬时限。续费快照失败后等下一周期重试，也不满足一个 OCI timer 周期内恢复。
   分歧：各单元会分别把时限从到期、任务启动、快照送达或成功重试时起算，得到不同验收结果。
   建议修法：统一起算点、成功条件和故障条件，分配调度、排队、推送及电源操作的时间预算；使关机不等待 HAPI 推送耗尽预算。若业务只要求健康条件下的时限，须同步修订 ticket，不能由实现自行放宽。

## medium

1. **位置：AD-3——状态图没有形成完整、确定的查询规则。**
   问题：图中没有覆盖 `no_expiry`、已过期但 VM 尚未关机、已过期同时存在人工原因、续费后仍人工停用，以及 Portal/PVE 查询失败等组合。首次进入“正常”还限定日期为当月月底，不能描述已经续到未来月份的员工。
   分歧：`hub-status`、提醒任务和员工展示可能对同一组事实返回不同状态，或把未知误报为正常。
   建议修法：补充有优先级的判定表，区分业务到期、接入原因、电源状态及查询未知，并明确孤儿资源如何呈现。

2. **位置：AD-2、AD-3、AD-21——禁止持久化状态与状态展示副本相互冲突。**
   问题：AD-3 禁止任何组件持久化生命周期字段，AD-21 却要求网站和小程序只读取执行器推送的状态副本，不自行推导；没有明确副本例外、schema、generation 或过期展示规则。公开 Semaphore 配置（`ansible/roles/semaphore/files/semaphore-bootstrap.py:44`）已每小时发布一次状态，进一步表明展示存在延迟。
   分歧：入口实现可能拒绝保存状态、改为自行计算，或无限展示旧的“正常”。
   建议修法：明确允许持久化可丢弃的展示投影，禁止把它作为业务权威；统一字段、生成时间、顺序控制和失效后的展示行为，并区分实时管理查询与缓存展示。

3. **位置：AD-2、AD-10、AD-13、AD-17、Deferred——设备包的存储与凭据规则未同步。**
   问题：AD-17 已决定含私钥的设备包在 D1 保存至退役或替换；AD-2 仍规定私钥只在运行时物化、设备包在 R2 临时存放，AD-13 仍称 D1 不存凭据，AD-10 删除顺序只点名 R2，Deferred 仍以“且即删”为依据。
   分歧：网站可能执行长期 D1 保存，凭据模块却禁止该写入；退役模块也可能只清理 R2，留下 D1 设备包。
   建议修法：按最新设备包决定统一所有权表、D1 凭据例外、上传和删除契约及保留期限；退役完成条件必须核验实际存储后端已删除对应设备包。

4. **位置：AD-13——Turnstile 降级规则弱化 ticket R1。**
   问题：R1 要求提交经过 Turnstile 校验并按 IP 限频，AD-13 却允许 Turnstile 无法加载时仅靠限频，没有获得 ticket 中的对应例外，也没有定义如何判定“无法加载”。
   分歧：网站单元可接受未验证申请，验收单元则会按 R1 拒绝；客户端故意不加载与服务故障也可能被同等处理。
   建议修法：采用验证失败即拒绝的规则；若确需降级，则先在 ticket 中明确授权条件，再固定服务端可判定的降级边界。

5. **位置：Structural Seed、AD-15、AD-22、AD-32、Deferred——部署与验收环境边界整维缺失。**
   问题：spine 已决定生产位置和部分发布路径，但没有决定验收使用独立环境还是共享生产环境，也没有划定 D1、BWS、Terraform state、Semaphore 任务和外部投影的隔离范围。ticket 同时要求测试员工退役、启动卷恢复和全量 endpoint 切换。
   分歧：各 epic 可能分别使用测试数据库、真实 catalog 或真实 Terraform state，使跨组件验收指向不同资源，或让测试改动进入生产投影。
   建议修法：补充部署与环境规则，至少明确环境数量、资源和凭据绑定、测试身份范围，以及跨系统验收允许操作的边界；单一共享环境也应作为明确决定写出。

6. **位置：Design Paradigm、AD-14、AD-18、AD-19、AD-21、Structural Seed——小程序的本期范围自相矛盾。**
   问题：ticket 的 2026-11-02 决定明确暂缓小程序、相关双入口能力及 uniCloud 到期提醒；spine 的主要规则仍将它们写成当前必需能力，仅目录树标注“搁置”。
   分歧：申请、提醒和前端单元会对是否必须部署 uniCloud、是否必须实现双入口采取不同解释。
   建议修法：统一标注本期生效范围与未来保留契约，把暂缓能力及其依赖明确列入 Deferred，避免用目录注释承担范围决定。

7. **位置：Stack、AD-29、AD-32——具名技术尚未达到“verified-current”的证据要求。**
   问题：Stack 声称 bpg/proxmox 的“2026-11 最新版本”、Semaphore 的“最新稳定版”，但未给核验来源；关键 SDN 目标版本仍交由实现 story 核验，恢复能力则明确尚需演练。公开代码只能证明当前钉住 bpg/proxmox 0.70.0（`terraform/remotecc/versions.tf:12`）、oracle/oci 8.3.0（`terraform/oci/versions.tf:13`）和 Semaphore 2.19.17（`ansible/roles/semaphore/defaults/main.yml:2`），不能证明“最新”或目标能力兼容。
   分歧：下层可能选择不同的 `<1.0` provider，采用不同的 SDN 接口和升级假设。
   建议修法：记录核验日期、官方来源及适用能力；在依赖单元实施前固定经过核验的 provider 版本。尚未验证的恢复行为应继续保留为显式前置条件，不作为已确认能力。
