## high

### H1 — 相同 generation 可以携带不同配对，防回放约束无法成立

**涉及 AD：** AD-2、AD-13、AD-27、AD-28。

**单元 A 如何合规构建：** 网站配对接口分别查询完整配对列表和 catalog generation，再返回 AD-13 指定的结构。AD 没有要求两次读取属于同一个数据库快照，也没有规定一个 generation 必须唯一对应一份内容。

**单元 B 如何合规构建：** `firewall.py pairs` 在本机锁内拒绝更旧的 generation，允许相同 generation 重放，并原子替换全部元素，完全遵循 AD-27。

**冲突：** A 先读到删除前的配对，随后发生删除并递增 generation，A 再读到新 generation。另一轮查询可以先将正确的新配对应用到 B；前一轮响应随后到达，因 generation 相同而被接受，将已撤销的配对重新装回。本机锁和原子替换都不能识别这种错误。

**如何收紧：** 明确规定配对内容与 generation 必须从同一一致性快照读取；所有影响配对的变更必须在同一事务内递增 generation；相同 generation 的规范化内容必须不可变。消费者对“相同 generation、不同内容”应拒绝并报警。落实位置是 AD-13、AD-27、AD-28，不能仅由某一侧自行约定。

### H2 — `no_expiry` 没有可互操作的 OCI 快照表示

**涉及 AD：** AD-8、AD-9、AD-12。

**单元 A 如何合规构建：** 快照生成器为免到期员工保留条目，将 `paid_through` 写为 `null`：既满足“全体员工”的要求，也不新增 AD-12 禁止的字段，更不为其伪造到期时间。

**单元 B 如何合规构建：** OCI 快照读取器将 `paid_through` 按文档的时间约定解析为带偏移的 ISO 8601 时间；遇到 `null` 判为无法读取，沿用上次有效快照，遵循 AD-9 的失败处理。

**冲突：** 文档没有规定 `null` 是合法快照值，更没有规定它必须清除已有的 `expired`。将已经到期的员工改为 `no_expiry` 后，B 可以继续沿用旧到期值并保持断开；若按整份快照校验，还会阻止其他员工的新到期值生效。把免到期员工省略也不能补救，因为 AD-9 明确规定缺席员工不处理。

**如何收紧：** 在 AD-12 固定快照 schema，例如明确 `paid_through: ISO8601 | null`，其中 `null` 唯一表示免到期；在 AD-9 规定遇到该值必须移除本组件的 `expired`，保留其他原因，并明确它与条目缺失的不同语义。

### H3 — HAPI schema 2 只固定了字段名，没有固定令牌结构与地址语义

**涉及 AD：** AD-5、AD-20、AD-23、AD-24、AD-26、AD-28。

**单元 A 如何合规构建：** `hub-hapi.roster()` 生成规定的员工字段，使用员工 overlay IPv4 作为 `address`；`hapi-sync` 将 BWS 令牌发送为 `tokens: {"<employee_id>":"<token>"}`。载荷标注 `schema: 2`，没有未知字段。

**单元 B 如何合规构建：** `hapi-ctl` 支持 schema 2，但将 `tokens` 定义为 `[{id, token}]`，将 `address` 定义为 VM 的物理 IPv4。它仍由唯一入口写动态文件、按员工 namespace 绑定令牌，并拒绝无法校验的输入。

**冲突：** AD-24 没有规定 `tokens` 的类型、成员结构，也没有界定 `address` 属于哪一种网络。两端可以都声明支持 schema 2，却在首次同步时拒绝载荷，或者接受地址字符串后生成不可达的路由。manifest 的 schema 检查无法区分这两种实现。

**如何收紧：** 在 AD-24 给出完整的版本化协议：字段类型、必填项、地址所属网络、令牌键与员工 ID 的关联，以及令牌字段缺省、空集合和部分集合的语义。生产者和消费者必须以这份协议定义“支持 schema 2”。

### H4 — 电源状态的所有者没有提供区分人工关机与到期关机所需的事实

**涉及 AD：** AD-2、AD-16。

**单元 A 如何合规构建：** PVE 适配层以 PVE 当前电源状态为事实，只报告 `running/stopped`。管理员对已经停止的 VM 再执行停止，不产生新的电源状态；AD 没有要求记录关机意图或原因。

**单元 B 如何合规构建：** `enforce` 在运行记录中保存自己成功执行的到期关机，续费后只恢复这些 VM，从而避免启动其他人工关闭的 VM；这没有持久化员工生命周期状态，也没有改变 PVE 的电源事实所有权。

**冲突：** VM 被到期任务关闭后，管理员在它仍停止时要求保持关闭，随后员工续费。A 的事实没有变化，B 的到期关机记录也仍成立；B 无法知道已有人工关闭意图，会重新开机。若 B 一律保留停止状态，又无法完成到期关机后的续费恢复。缺失的是跨单元共享的操作意图契约。

**如何收紧：** 在 AD-2 明确人工电源保持意图的所有者、存储位置和操作入口；在 AD-16 固定其与自动恢复的优先级、清除条件，以及运行检查点的有效期。不能仅凭当前电源状态或最后一次自动关机记录推断人工意图。

## medium

### M1 — 多入口“合并一条申请”没有定义可执行的统一申请身份和字段优先级

**涉及 AD：** AD-5、AD-6、AD-19。

**单元 A 如何合规构建：** `wsctl request` 保存带来源前缀的原始文件，同邮箱只展示一条合并结果，并标出两个来源；展示时选取最新申请的规格和联系方式。

**单元 B 如何合规构建：** `provision --request <申请 ID>` 按指定的原始请求文件读取邮箱和基本信息，完成后只回写该原始申请的入口。AD-6 要求信息来自请求文件，AD-19 没有规定合并结果必须成为独立的开户输入。

**冲突：** 同一邮箱在两个入口填写不同规格时，管理员看到的合并申请可以与开户读取的文件不同。两个入口还可以拥有相同的本地申请 ID；文件名虽然已区分来源，命令参数的身份规则仍未固定。完成后究竟处理一个来源还是全部合并来源，也没有统一解释。

**如何收紧：** 在 AD-19 定义统一申请引用、字段冲突规则及其来源列表；AD-6 必须消费这一确定的合并结果，并将其纳入审批摘要。明确成功或 dismiss 后应回写哪些原始申请，以及部分回写失败如何续跑。

### M2 — 状态展示副本没有版本约束，旧重试可以覆盖续费后的新状态

**涉及 AD：** AD-2、AD-18、AD-21，以及“幂等、检查点续跑”约定。

**单元 A 如何合规构建：** 执行器从事实推导状态，同时推送网站和 uniCloud；某入口失败时保存待重试载荷，之后重放，不让一个入口失败阻塞其他工作。

**单元 B 如何合规构建：** 网站和 uniCloud 只存执行器提供的展示副本，不自行推导，收到推送就替换。两个入口使用相同字段，满足 AD-21。

**冲突：** 一次“已到期”推送失败并进入重试；随后续费产生的新状态已成功推送。旧任务恢复后，B 仍会接受“已到期”并覆盖新状态。唯一推送者和串行执行都不能阻止较旧业务结果在较晚时间重放，文档也没有保证何时再次修正。

**如何收紧：** 为展示副本规定完整 schema、员工键和单调递增的投影版本；接收端拒绝旧版本，相同版本只允许相同内容。明确删除、退役及同邮箱重新开户的版本边界，并规定重试使用原载荷还是重新读取事实。
