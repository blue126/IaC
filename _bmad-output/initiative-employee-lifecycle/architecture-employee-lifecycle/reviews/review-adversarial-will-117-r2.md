**high**

1. **开户中的已启用资源可能永远落在到期执行范围之外。**
   涉及 AD-6、AD-9、AD-12、AD-16、AD-27、AD-28。

   **单元 A：开户编排。** 先保存 VM、设备与 `paid_through`，登记 Portal 身份，按 AD-27 填充配对后启用设备，再验证配置并写入设备“已配置完成”的事实。AD 没有要求最后这项事实必须先于启用写入。若启用后进程中断，运行记录可以保留待续跑。

   **单元 B：生命周期执行。** 按 AD-28 使用 `catalog()` 获取在册员工；由于该设备尚未被记为配置完成，该员工不在结果中。到期关机只操作 catalog 员工，OCI 快照也可以由这份员工集合生成；AD-9 又要求不处理快照外的员工。

   **冲突：** VM 和 WireGuard 已经可用，但到期断开与关机均不覆盖它。即使 D1 已保存过去的 `paid_through`，只要开户没有续跑，这个空档就能无限持续；配对接口明确包含开户中的记录，不能补上生命周期执行的缺口。

   **收紧：** 明确“允许接入的资源集合”必须包含于“到期执行覆盖集合”。首次启用前，须让计费事实及身份进入到期执行使用的权威查询，并确认 OCI 已接受相应快照；或者让到期执行覆盖全部 VM 记录，将“在册”过滤仅用于展示。

2. **最后一名员工退役产生的空集合，与 IaC 管理的 HAPI 校验器不兼容。**
   涉及 AD-10、AD-22、AD-23、AD-24。

   **单元 A：`hapi-ctl`。** 最后一名员工退役后，`hapi-sync` 提交空名单和空令牌集；按照 AD-23 的回收条件，生成空的 `credentials`、`agents` 集合。禁止发送空名单的是 `enforce`，没有禁止 `hapi-sync` 发送。

   **单元 B：IaC 与服务启动。** 按 AD-22 保留 IaC 所有的 `hapi-hub-config.py`。公开源码中的 `credentials()` 和 `agents()`（`ansible/roles/hapi-shared-hub/files/hapi-hub-config.py:34`）都要求集合至少有一项；Ansible 角色（`ansible/roles/hapi-shared-hub/tasks/main.yml:113`）和 Hub 启动单元（`ansible/roles/hapi-shared-hub/templates/hapi-shared-hub.service.j2:14`）都会调用它。

   **冲突：** 如果动态写入路径调用这项校验，最后一次退役无法完成；如果动态路径允许写入，下一次角色运行或 Hub 重启会失败。AD-24 的输入 `schema` 兼容检查不能发现这个派生文件契约冲突。

   **收紧：** 规定零员工、零令牌是合法且可启动的状态，禁止通过保留虚假员工满足校验。同时将派生文件格式、空集合语义及其 IaC 校验器、Hub 消费者纳入明确的兼容契约；发布门禁不能只检查 `wsctl → hapi-ctl` 的输入 schema。

3. **HAPI 名单的 `address` 没有确定地址空间语义。**
   涉及 AD-2、AD-24、AD-26、AD-28。

   **单元 A：`hub-hapi.roster()`。** 从 catalog 读取员工 VM 的 overlay，填入 AD-24 的 `address`；地址在执行器算好、载荷使用 schema 2，均符合规则。

   **单元 B：HAPI 渲染与网络。** 将 `address` 当作 VM 的物理地址，生成 9443 上游；PVE 防火墙按 AD-26 从 VMID 派生物理地址及 HAPI 放行规则。现有公开的 worker 地址校验（`ansible/roles/hapi-shared-hub/files/hapi-hub-config.py:69`）仅检查私有 IPv4，不能区分物理地址与 overlay。

   **冲突：** 两种地址都能通过字段及 schema 校验，但生产者提交的目标不属于接收方配置的网络路径；9443 连接因此失败。AD 对 WireGuard 配对明确限定了 overlay，对 HAPI 的同名地址字段没有对应限定。

   **收紧：** 明确 schema 2 中 `address` 究竟取哪个事实、属于哪个地址空间、是否带前缀，以及它与监听地址、PVE 放行规则的对应关系。为同一 VM 同时给出物理地址和 overlay 的契约示例，避免两边碰巧使用相同测试值。

**medium**

4. **展示投影的 generation 可以合规地递增，但运行状态仍永久停留在旧值。**
   涉及 AD-2、AD-3、AD-18、AD-21。

   **单元 A：状态发布器。** 每当 catalog generation 前进，就重新推导状态并发布整份投影，使用 catalog generation 作为投影 generation。每次实际发布的值都严格递增；AD 没有规定其他发布触发条件。

   **单元 B：网站和 uniCloud 接收端。** 严格拒绝不更大的 generation，只显示执行器推送的状态，不自行推导。

   **冲突：** 时钟越过到期日、Portal 人工停用或 PVE 电源变化，都可以不改变 catalog generation。两端继续显示“正常”，直到发生下一次 catalog 写入；网站甚至可以同时显示已经过去的到期日和旧的正常状态。

   **收紧：** 区分 catalog 修订号与展示投影发布序号。规定发布器在时间边界及 Portal、PVE 事实变化时刷新投影，或给出周期刷新上限；投影内容变化必须推进发布序号，即使 catalog 未变。

5. **来源前缀只固定了文件名，没有固定命令使用的申请标识。**
   涉及 AD-5、AD-6、AD-19。

   **单元 A：申请汇总器。** 将不同邮箱的两份本地编号 `42` 分别保存为 `site-42.json`、`mp-42.json`，列出各自来源，满足来源隔离和文件命名规则。

   **单元 B：命令解析器。** 按 AD-6 接受 `--request 42` 或 `--dismiss 42`，优先查找网站文件；随后严格从找到的请求文件取邮箱，并只回写它所属的入口。

   **冲突：** 管理员针对小程序申请执行的命令可以选中网站申请。开户计划可能让管理员发现错选，但 `dismiss` 没有同样的审批保护；两个组件均遵守文件前缀规则，接口仍然存在歧义。

   **收紧：** 将跨入口的规范标识定义为 `site-<id>`、`mp-<id>`，要求列表输出、命令参数、运行记录和回写定位统一使用它；裸 ID 必须拒绝。合并同邮箱申请时，还需保留完整的来源标识集合。

6. **“到期后 3 天”的退役边界允许两种不同的时间计算。**
   涉及 AD-3、AD-8、AD-10 及时间约定。

   **单元 A：状态查询。** 将 `paid_through` 转换到 `Australia/Sydney`，增加三个当地日历日，再判断是否可退役。

   **单元 B：退役命令。** 将带偏移的 ISO 8601 时间转换为时间点，增加固定 72 小时，再执行候选筛选与提交前复核。

   **冲突：** 当夏令时切换落在这三天内，两者相差一小时。状态页与退役名单会对同一员工给出不同资格判断；现有“是否到期”共用实现的要求没有覆盖退役等待期。

   **收紧：** 明确等待期是固定 72 小时，还是三个悉尼日历日，并固定严格比较边界；状态查询、计划生成及提交前复核必须共用同一个退役资格函数。
