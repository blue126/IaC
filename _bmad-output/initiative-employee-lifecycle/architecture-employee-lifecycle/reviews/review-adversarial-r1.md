结论：该更新仍存在 7 组可由各自遵守现有 AD 的下层单元构成的不兼容实现，涉及 Terraform 输入集合、地址算法、配置类型、Hub 协议、并发投影、恢复放行和退役竞争，Reviewer Gate 应先收紧对应规则。

以下均为架构允许的反例构造，不代表现有私有代码已经存在这些缺陷。

1. **high — D1 中的 VM 记录与过滤后的员工集合，可以生成不同的 Terraform 目标集合**

   **单元 A：开户执行器。** 遵守 AD-2、AD-3、AD-28：先在 D1 写入 VM 记录，再生成包含该记录的 var-file 创建 VM；开户尚未完成，因此 `catalog()` 不向其他模块返回该员工。假设创建后、完成开户前执行中断。

   **单元 B：后续 Terraform 输入生成器。** 遵守 AD-2、AD-28：运行时从 D1 的 `catalog()` 生成 var-file，不使用 roster，也不持久化生命周期状态。它只得到已在册员工，因此遗漏 A 已经创建的 VM。

   **冲突：** AD-28 同时引入“开户前写 VM 记录”和“`catalog()` 隐藏开户中记录”，却没有规定 Terraform 必须读取哪个全量视图。B 的下一份目标集合可以把 A 的 VM 当成应删除对象；审批只能展示这个错误目标集合，不能修复集合语义。公开 Terraform 实现确实以输入 map 的键驱动资源存在性（spine AD-28、`terraform/remotecc/oci-hub-workspace.tf:55`）。

   **关闭规则：** 收紧 AD-28：明确区分“全部 VM 意图记录”和“在册员工投影”；Terraform 必须读取前者，包含尚未完成开户但仍需保留的 VM，禁止通过过滤后的 `catalog()` 构造资源全集。同时定义唯一的在册推导谓词。

2. **medium — Terraform 和防火墙可以采用不同的 VMID 派生算法，并通过全部现有迁移检查**

   **单元 A：Terraform 输入适配器。** 遵守 AD-25、AD-28、AD-29：VMID 是输入，VNet、物理地址、网关和 MAC 均由确定性函数计算，不另存员工网络配置。

   **单元 B：PVE 防火墙及启动 hook。** 遵守 AD-26：独立按 VMID 算出期望值，校验本机对象，不符即拒绝加载和启动。

   **冲突：** Spine 没有定义算法、适用 VMID 范围或地址域。可以构造两个函数：对所有现有 VMID 完全相同，对某个将来分配的 VMID 不同。因此“现有 VM 全符合算法”和“新渲染与线上一致”两项检查都能通过，新增 VM 却被 B 拒绝启动。公开 Terraform 当前接收显式地址和 MAC，也未提供这里所需的统一派生算法（spine AD-26、`terraform/remotecc/oci-hub-workspace.tf:6`）。

   **关闭规则：** 收紧 AD-26、AD-28：指定唯一算法及版本、VMID 有效范围、越界处理和跨网段进位规则，双方复用同一实现或同一规范向量。明确“由 VMID 派生的地址”是物理地址还是也包含 AD-2 中由 catalog 所有的 overlay。

3. **high — 同一个 `endpoint` 可以被一个单元当作 IP，被另一个单元当作完整 WireGuard 端点**

   **单元 A：IaC 配置及 PVE 防火墙。** 遵守 AD-2、AD-25、AD-26：把唯一的 `endpoint` 定义为裸 IPv4，例如 `203.0.113.20`，据此生成 OCI Hub 的 UDP 51825 放行规则。

   **单元 B：员工 VM 配置及设备包生成器。** 遵守 AD-2、AD-25 和 IP 变更预案：只读同一个 IaC `endpoint`，把它作为完整 WireGuard `Endpoint` 写入配置，不再维护 settings 副本。

   **冲突：** 所有者统一了，类型和转换规则没有统一。裸 IP 不能直接满足完整 WireGuard 端点的要求；反过来使用 `IP:port`，也不能直接满足防火墙的 IPv4 输入，而且设备和工作区使用不同端口。公开旧防火墙将 `endpoint` 按 IPv4 校验，Spoke 模板则直接输出 `oci_hub_spoke_endpoint`，因此这是真实存在的两种消费语义（`scripts/oci-hub/boundary.py:43`、`ansible/roles/oci-hub-spoke/templates/wg-workspace.conf.j2:8`、`oci-hub-ip-change.md:15`）。

   **关闭规则：** 在 AD-25 固定唯一配置位置、类型及有效值解析方式；例如只保存 Hub IPv4，由消费者分别派生设备端点、工作区端点和防火墙地址。同步规定 Vault、Ansible 变量优先级和插值如何解析，确保 `wsctl` 读取的是与 role 相同的有效配置。

4. **high — Hub OS 层和私有执行器可以分别实现完整功能，却无法交换配置与配对**

   **单元 A：`oci-hub` role 和 `firewall.py`。** 遵守 AD-27、AD-30、AD-31：role 独占配置和防火墙代码分发，生成 `executor.json`；`pairs` 从 stdin 接收完整列表并事务替换 set。例如选择对象列表 `[{device, workspace}]`，配置中使用嵌套 `portal.api_token`。

   **单元 B：`executor.py`。** 遵守 AD-27、AD-31：只读 role 生成的配置，从账本计算完整配对，只调用 `firewall.py pairs`，不生成 nft 语法。例如选择二元数组列表，并从 `portal_api_token` 读取令牌。

   **冲突：** AD-27 说双方共享输入格式，但没有给出该格式；AD-31 只指定配置写者，没有指定配置 schema。两种实现都能满足文字规定的职责，却不能互操作。AD-27 的“先发布执行器，再切规则”也没有要求新执行器在旧防火墙尚无 `pairs` 能力时保持兼容；AD-30 的“最新 checkout”不能保证独立发布的私有执行器兼容。公开当前 role 对执行器配置直接进行 JSON 序列化，没有补足这个契约（spine AD-27、`ansible/roles/oci-hub/tasks/main.yml:96`）。

   **关闭规则：** 新增 Hub 协议 AD：固定 `pairs` 和 `executor.json` 的版本、字段、地址表示、空列表含义、校验及失败行为；规定公开 OS 包与私有执行器的兼容矩阵。切换前必须确认双方能力，先发布阶段必须支持旧模式或明确阻止不兼容操作。AD-24 已为 HAPI 提供同类先例。

5. **high — 防火墙重载可以把刚退役的配对重新写回**

   **单元 A：role 触发的防火墙重载。** 遵守 AD-27、AD-30：读取当前 set 元素，渲染新规则，并在事务中恢复所读取的元素，实现“重载保留元素”。

   **单元 B：Hub 退役执行器。** 遵守 AD-10、AD-27：删除账本身份，再调用 `pairs`，以完整列表事务替换 set，去掉该配对。

   **冲突：** 合法交错为：A 读取旧元素 → B 完成退役和 set 替换 → A 提交保留旧元素的重载。两个 nft 事务各自原子，仍会恢复已删除配对。执行器内部串行和 `wsctl` 运行锁不覆盖 role 触发的独立防火墙重载；规则校验又明确排除 set 元素。下一轮对账之前，运行态与账本相反。

   **关闭规则：** 收紧 AD-27：所有读取并改写 set 的动作，包括重载和 `pairs`，必须使用同一主机锁，将读取、校验和提交纳入同一临界区；禁止较旧投影覆盖较新投影。明确该锁与执行器锁的关系及失败行为。

6. **high — 恢复流程可以先放行备份中的旧身份，再清除它们**

   **单元 A：Hub 启动与配对执行器。** 遵守 AD-2、AD-27：恢复后以本机账本 `identities` 为有效配对所有者，首次周期立即填充 set。恢复的 Portal 数据库也可以包含当时启用的旧 peer。

   **单元 B：恢复协调器。** 遵守 AD-32 和“配置总览”：恢复启动卷、运行 role、让执行器校对账本和 set，然后才推送快照并按当前 D1 双向对账。

   **冲突：** 若备份之后发生退役、设备撤换或改址，A 会在 B 对账前恢复旧身份的网络通路。结合 AD-10 允许 overlay 和设备地址复用，旧设备甚至可能命中新分配工作区。两者严格遵守表中的顺序，仍存在旧权限重新生效的窗口；最终对账成功不能消除之前的错误放行。

   **关闭规则：** 收紧 AD-32：恢复启动必须进入隔离模式，在新鲜 D1 全量对账、身份归属校验和到期快照安装完成前禁止业务转发，不能先按备份账本填充可通行的 set。AD-27 的正常启动行为必须显式服从该恢复门禁。

7. **high — 退役的执行前检查不能排斥合法的 D1 控制台续期**

   **单元 A：批量退役执行器。** 遵守 AD-1、AD-10：完成审批和执行入口校验，开始处理某员工前重新读取 `paid_through`，确认仍符合条件，然后按规定顺序删除 Portal、账本、VM 记录和 VM。

   **单元 B：管理员 D1 控制台写入。** 遵守 AD-2 的明确例外：在 A 已完成该员工的重新读取之后，将其 `paid_through` 延长。B 不经过执行器运行锁。

   **冲突：** A 的检查与不可逆销毁之间没有共同互斥或条件提交契约。B 的合法续期可以在检查后成功落库，A 仍继续删除已付费员工的 VM。审批时和执行前都正确检查，也无法关闭这个窗口；单执行器不能串行化控制台写入。

   **关闭规则：** 收紧 AD-2、AD-10：取消不受约束的控制台直接续期，或使所有续期参与同一员工级互斥协议。退役必须通过 D1 条件操作取得排他权并绑定记录修订，续期与销毁必须有明确、唯一的竞争胜负规则，不能只增加一次读取。
