当前阶段继续由管理员发起开户，沿用每员工独立 VM、每设备独立身份，并通过 Temp.sh 和邮件交付设备包。本方案不实施申请门户、邮箱验证领取或自动开户 CD；本记录不创建定时任务或自动触发部署。员工无需 GitHub 账号仍是后续自动化方案的明确要求。

用户要求将已发布的本机 bootstrap 扩展成“员工申请 → 管理员批准 → CD 下发”，并已明确申请不应要求 GitHub 账号。员工侧使用网页申请和受保护的完整项目 ZIP 领取；GitHub 仅供后台维护代码及管理员审批变更。当前客户端项目 1.0.0 已发布；本文所述门户与服务端自动开户尚未实现、启用或验收。

## 员工和管理员的操作

1. 员工打开无需 GitHub 登录的 HTTPS 申请页，填写姓名、联系邮箱、设备名称、操作系统和用途，通过邮箱验证码确认能接收该地址的邮件。不提交公钥或个人 Claude 凭据；邮箱验证只证明邮箱控制权，员工身份仍由管理员核实。
2. 系统生成待审开户变更和部署预览，显示申请人、VM 配置、设备数量、分配结果及预计影响。
3. 管理员核实申请人及其领取邮箱并确认合并后台开户 PR。这是本次开户的一次最终批准，批准范围包含对应 VM、设备身份、必要路由及隔离配置，以及只向该申请人提供的完整 bootstrap 项目。员工不需要查看或访问这个后台 PR。
4. Jenkins CD 执行已经批准的变更，验证服务端后构建包含设备包及实际配置单的专属项目 ZIP，存入私有交付存储。系统向获批邮箱发送就绪通知和门户领取地址，邮件不附私钥或完整设备包。
5. 员工在领取页用获批邮箱的短期验证码完成验证，下载并解压一个完整项目，交给自己本机已有 Agent 按 README/AGENTS 完成 bootstrap。不需要 GitHub、Git 或另行寻找设备包；系统 VPN 权限和个人 Claude 登录仍交本人确认。

审批前查看后台 PR 和预览，最后合并是一个审批关口；不在部署后再要求管理员手工建 VM、分配地址、打包或邀请员工注册 GitHub。专用开户任务不能照搬当前通用 Jenkinsfile 的两个独立部署确认，否则不满足一次批准的目标。此变化只适用于经过校验的开户变更，不修改其他部署的审批方式。

申请入口已确定为无需 GitHub 账号的网页。申请及领取页必须在开通员工 WireGuard 之前可达，不能设在仅有 VPN 才能访问的位置。域名、部署位置和发信服务在实施时结合现有可用资源确定；本次修订不创建公共仓库、发布网站或配置外部发信凭据。

## 保持的分配与使用规则

每个员工一个独立持久 VM，每台设备独立 WireGuard 地址和密钥及 SSH 身份，设备只映射所属员工 VM。员工拥有本人 VM 的 sudo，管理自己的依赖和工具。沿用 CPU host 和现有默认 2 核、4 GiB、50 GiB 规格；申请表不接受任意 node、VMID、桥、地址、镜像、命令或软件安装脚本。

新增员工使用尚未分配的永久槽位；当前 pilot/control 已占用两个，不因测试用途擅自回收。现有实现最多十个永久 NIC 槽位，停用仍保留分配，因此不能宣传无限开户。检查容量和实际 VMID/网络占用后才生成审批预览，容量不足返回明确失败。

新增设备应复用员工已有 VM，生成新的设备身份及独立交付项目；不得复制同一份设备包给多台电脑。申请记录区分新员工开户和已有员工增加设备，不默认为第二台设备另建员工 VM。

保留 workspace-login 和 workspace-browser，首次个人 Claude OAuth 在澳洲 VM 内完成。本机 Agent 不读取个人登录文件、验证码或浏览器会话，CD 不预置管理员个人 Claude/MCP 配置。

## 审批与执行的绑定

申请是数据，不是可运行代码。执行程序始终来自受信任的 IaC 发布版本；申请内容、页面参数或申请人的代码不能作为 shell、Ansible 任务或流水线源码执行。

准备阶段生成规范化申请摘要、固定员工/设备分配、严格限制路径的开户 PR，以及受保护的 Terraform plan。只允许修改本次必要的员工名单和加密身份数据；流水线源代码、凭据配置和其他基础设施不属于开户申请可以修改的范围。PR 检查不取得生产凭据，也不执行部署；受信任 Jenkins 的准备任务负责需要生产只读权限的预检。

管理员批准绑定内部申请 ID、已核实员工身份、已验证领取邮箱、申请内容摘要、受信任工具版本、开户 PR 的内容和部署变更摘要。修改收件人、员工、设备、规格或实际部署范围必须重新批准；普通标签、页面状态和伪造的 webhook 字段不是批准。

合并后的专用任务重新验证所有绑定，使用审批对应的计划。计划因状态变化过期时停止；不能在旧批准下自动应用更宽的新计划。Terraform plan 本身可能含秘密，不能直接作为 GitHub Issue、PR 评论或普通构建附件公开；只展示脱敏变更摘要。

当前共享 HCP Terraform workspace 还有其他服务：不得直接执行全量 apply 来顺带处理无关变更。开户执行串行，并与会写同一员工名单/BWS 凭据记录的任务协调；HCP 状态锁不能单独代替分配锁。计划出现无关 VM、员工磁盘删除/替换、既有分配变化或未批准的网关重启时停止。

## CD 执行顺序与交付

准备阶段分配资源并在加密 Vault 中保存本次所需身份，重跑同一申请复用原身份。VM 主机身份应在可信管理路径中确定，不能用未核实的 ssh-keyscan 结果直接当作信任依据。准备阶段不能复制 pilot 的设备或浏览器登录文件。

批准后的顺序是：安装本次 VM 的外部隔离与网络前置配置 → 创建/配置个人 VM → 部署 Claude 与登录/浏览器助手 → 配置设备固定映射和必要路由 → 验证服务端 → 构建私密项目 ZIP → 开放本人领取并回写状态。实际 Terraform 资源依赖、首次启动和边界加载顺序仍需按当前角色验证，不能因有步骤列表就认为没有短暂暴露窗口。

交付采用每设备一个完整项目 ZIP，例如 workspace-employee-device.zip，包含 README/AGENTS、三平台入口、对应工具源码和 deployment 下的该设备包、摘要及实际配置单；员工始终只需要一个项目。通用客户端源码从固定清单取出，不带 .git 历史，不执行 fork/完整复制当前 pilot 仓库，因为其历史和 deployment 包含 pilot 密钥。

GitHub 保留在后台维护通用源码、IaC 和开户审批 PR，不再要求为每个无 GitHub 账号的员工建库或邀请协作者。后台源码/配置自动化使用专门、可撤销的凭据；不提取操作者 gh 登录令牌塞进 Jenkins。当前 pilot 私有仓库和已交付包不因新流程失效，也不向所有员工开放。

项目可以先在受保护的执行环境中构建，但只有服务端验证和包内容检查通过才开放申请人领取。发放前验证：存储及下载没有匿名读取权限、收件人匹配批准身份、源码版本匹配、ZIP 只含该设备数据、没有其他员工/管理端/Claude OAuth 凭据、bootstrap check 可解析内置包。真实设备包不进入公共 CI、普通日志或共享构建附件。

本机系统授权、真实 WireGuard 握手、交互 SSH/SFTP 和个人 OAuth 不能由服务端单方面宣称通过。CD 完成状态叫“已交付，等待员工接入”，通过员工验收后才叫“已接入”。

## 门户与私密领取

员工页面只有申请、查看本次状态和领取项目。申请及验证码接口设请求大小、邮箱/来源限速和发送配额；不向匿名访客公开员工名单、申请内容、环境详情或是否已开户。邮箱验证不是在员工申请前额外创建密码账号，不要求先连接 VPN。

领取地址只是门户入口，不是永久公开 ZIP URL。员工打开后请求向已批准邮箱发送短期验证码；验证码绑定申请版本、邮箱和用途，安全随机生成，仅保存验证所需的安全摘要，限次验证、到期失效并在成功后原子消费。领取时再次检查申请仍有效且未停用，建立仅可访问该设备项目的短期会话。邮件预览器打开链接不会直接消费领取资格或触发下载。页面不加载第三方统计脚本，不缓存敏感响应，日志不保存验证码或认证会话。

私密文件存储不开放静态目录/公共对象链接；下载必须经认证服务校验授权。CD 只有按请求上传/发布交付的受限接口，公开申请服务不持有 PVE、路由器、Vault 或 Jenkins 管理权限。申请只能进入待审核状态，不能让匿名 POST 直接执行 Terraform。管理员仍通过既有受保护的 GitHub 后台批准，申请页面不暴露管理端入口或自动批准接口。

重发、断点/下载失败恢复和会话到期后重新领取要有明确行为，不能将第一次 GET 设置成无法恢复的永久作废。交付保存时间及补发策略在上线配置中明确；过期补发重新验证原批准身份，改邮箱重新审批。发信服务及私密存储是新流程必需能力，目前未假定已配置，未实际发送通知。

## 重试与失败

以申请来源的稳定 ID 加申请版本作为请求标识，同一版本不重复创建 VM、槽位、密钥或交付项目。已有员工申请新设备与重复提交应识别出来，不能盲目新建环境。部署前持久保存分配和加密密钥，Jenkins 临时工作目录不能是唯一副本。

状态包括待准备、待批准、已批准、部署中、服务端验证失败、交付失败、已交付待接入、已接入、拒绝。状态以门户申请记录和已批准的 IaC 配置/分配记录为依据，构建号关联执行证据；后台 PR 只引用申请的必要字段，不复制验证码或下载会话。

部署失败默认停止开放下载和就绪通知；不自动删除持久 VM/磁盘来“回滚”。私有交付上传结果不明时按原请求和包摘要核实，不重复生成身份。交付或通知失败可以从已验证环境继续；重新领取需要重新验证原批准邮箱，不重新开户。申请修改或审批撤销使尚未开始的执行失效；已部署环境的撤销走现有停用流程，取消门户申请不能假装已经回收了环境。下载权限过期或失效不会自动撤销已经发到设备上的密钥，需要另行执行设备撤销。

## 实施与上线验收

先将现有部署实现整理到可追踪版本；当前 IaC 中后续部署变更仍未提交/推送，CD 不能依赖本机未提交文件。提交、推送及启用新任务分别按用户授权处理。

实现后先用合成申请和外部调用替身验证：未批准零部署、审批者校验、申请修改使批准失效、重复请求复用分配、不同员工/设备隔离、恶意字段被拒、无关 Terraform 变化停止、失败不开放下载、邮箱被改后不能沿用批准、验证码过期/重放/跨申请领取被拒、重复通知不重复开户、不泄露包或密钥。只模拟结果的测试不标作真实部署成功。

启用前给管理员查看最终申请/领取页、审批预览、发信及存储配置、服务凭据/权限、实际执行节点、精确变更范围和重试行为。随后以一个明确获准的测试申请贯通：申请 → 合并批准 → 部署 → 交付 → 中国侧设备 bootstrap/接入验收。实际新增路由与基础设施包含在该次明确批准范围中，既有 pilot/control 的批准不能替代。
