# HAPI 应用开户阶段候选实现

状态：已实现候选代码和隔离回归，尚未部署或完成真实员工验收。用户选择暂不在新Sandbox安装BWS SDK，因此真实SDK对接继续延期，缺依赖时执行会在外部写入前停止。正式私有入口目前仍使用此前已提交的基础设施版本；新应用命令先保留在任务工作树开发副本中。

这里的HAPI Hub是VM500上的应用服务，负责网页、会话数据库与Runner通信；OCI WireGuard Hub是独立VPN网关，不使用本流程的state或凭据。

## 阶段与就绪

| 阶段 | 候选命令／组件 | 完成边界 |
|---|---|---|
| 基础设施 | 原`request`／`plan-infra`／`apply-infra` | 原state、VM外边界和启动门禁通过，仅`infrastructure_ready` |
| 应用计划 | `plan-app --request-id ... --profile ...` | 绑定已存在的自有VM、SMBIOS UUID及经PVE/QGA取得的SSH公钥；生成独立审批摘要 |
| 应用准备 | `apply-app --plan ... --approved-sha256 ...` | 依次确保BWS材料、VM500登记、worker应用、真实服务回读、专用Access策略及待确认身份 |
| 本人身份 | 同源一次性确认页面 | 真实签名Access JWT与获批邮箱相符，本人POST确认后写入持久SQLite证明，不直接启用应用 |
| 应用启用 | `complete-app --plan ... --approved-sha256 ... [--wait-seconds ...]` | 读取本人证明，重新核验服务，启用本人路由并回读，仅置`route_enabled`；公网入口验收前`public_entry_ready=false`，个人Claude授权和员工验收单独记录 |

`complete-app`可短期等待本人确认，默认不等待；没有永久轮询服务。它只轮询该申请的身份证明，证明出现后才重新核验基础设施和应用。没有发送邮件或其他外部消息，私有handoff文件提供统一网址、首绑链接及说明。

## VM500与员工VM

`hapi-worker`角色在任何包／凭据写入前核对新VMID、真实product UUID、IP、MAC及申请所有权，拒绝500／501／502和已有员工Hub的基线。随后复用原生Firefox／Claude基线与`claude-login-agent`，只部署Runner、连接VM500 HAPI应用的loopback适配器和登录专用mTLS端点，不创建员工侧Hub。

worker只取得自己的API凭据及两种用途分离的叶证书。共享Hub签名密钥和CA签发私钥不分发。工作区ID保留`control-plane`、`hub`等基础设施身份，不能给员工派生同名客户端证书。VM500登记阶段只接收租户凭据及公有信任材料，不接收worker叶私钥；后者仅在私有管理区和本人VM。浏览器cookie、Access断言、Authorization和CSRF头在登录执行代理中清除。

## BWS和VM500登记

候选助手`bws-workspace.py`使用HapiWorkspace专用授权，校验实际项目与配置一致。每申请的材料绑定request ID、VMID、product UUID、地址及固定namespace。先持久化私有staged材料再创建秘密；重复执行核对既有值，不轮换或认领另一申请的材料。材料曾由本机回执或申请日志确认登记成功后，登记行缺失即拒绝重建；初次创建中断可继续核对并完成。

CA签发私钥只在管理员SDK进程内使用，输出只有worker叶身份、公有CA／CRL及其租户凭据。证书含独立client/server用途、SAN、SKI／AKI和KeyUsage；有效期受所有相关CA和CRL约束。现有VM500登记与BWS按逐凭据摘要核对，其他尚未发布的申请不会被删除或覆盖。

`hapi-registration`仅在VM500应用配置中合并本人凭据／agent、精确9443源地址例外和公有信任。源地址例外保存在独立`/etc/hapi-application/firewall.json`，由显式支持HAPI扩展的防火墙控制器加载；不改写`employee-access.nft`或其基线摘要。基础防火墙重新加载后重放HAPI例外，校验时只排除与独立策略完全相同、位于invalid-state丢弃之后的规则。其他登记保持不变；Nginx平滑reload，HAPI应用服务和其他Runner不重启。Ansible变量以私有加密runtime Vault留存用于失败核对，不将服务秘密放入inventory或日志。

## Access策略与首次身份

应用profile明确选择既有HAPI Access app及获批的allow策略模板。新策略以申请ID命名、仅include该员工的明确邮箱，保留模板的MFA、require／exclude及会话约束，追加到策略末尾；不编辑既有员工策略或全局设置。已确认策略被删除／修改时停止，不能用旧创建计划悄悄恢复授权。

VM500上的确认页面使用既有Cloudflare登录，只额外确认工作区归属，不要求HAPI基础token。GET不写绑定，POST校验同源／CSRF。证明包含issuer、AUD、邮箱、subject、申请ID、工作区ID、代次、nonce摘要及验证时间。唯一约束阻断重绑定和跨人占用；后台没有接受手填subject的参数。

入口在真实服务和证明同时通过前保持关闭。身份确认后页面等待启用并返回同一origin；个人Claude授权仍由本人在VM内完成，已有登录不主动登出。

## 失败、恢复与限制

逐阶段保存意图及回读，结果不明按固定ID核查；失败先阻断本人公开入口，保留VM、BWS材料及其他人的工作区。启用回执丢失后先阻断本人入口并清除服务就绪标志；需按原获批申请重跑`apply-app`核查应用阶段，再运行`complete-app`，不只是重试最后一次启用。已就绪工作区后来验证失败不会继续显示已验证ready，也不会用旧创建授权覆盖外部撤权；这类日常恢复需要独立明确的恢复计划，完整停用／恢复生命周期尚未交付。

当前证据包括真实Unix HTTP/RSA身份绑定、实际Ansible渲染的Nginx/mTLS、OpenSSL严格证书验证，以及合成外部阶段的审批／失败／回执丢失回归。真实SDK、实际CF写入、真实worker安装及完整员工首次Claude授权没有执行；它们不能由这些隔离结果替代。
