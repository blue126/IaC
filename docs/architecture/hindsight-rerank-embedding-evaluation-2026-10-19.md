# Hindsight 重排与嵌入第二轮评估（2026-10-17～19）

第一轮评估（[多语言重排模型评估](./hindsight-multilingual-reranker-evaluation.md)，2026-10-10）把重排换成了 mmarco。之后记忆被统一转成英文（2026-10-17），中文提问配英文记忆变成了跨语言检索，mmarco 的中文排序明显下降；记忆库变大后重排也变慢。本文记录第二轮的对比测试、结论和上线结果。部署与运维细节见 [hindsight-memory-architecture.md](./hindsight-memory-architecture.md) 和 [hindsight-operations.md](../guides/hindsight-operations.md)。

**证据口径**：数字来自 2026-10-17～19 的实测（实测记录）。相关性标注由执行评估的 agent 一人完成；测试集是两个库的 36 条查询（18 个话题 × 中英文各一），后期改用线上客户端参数召回出的真实候选池（32 条，4 条的标注答案因后台整理已不存在）。样本小，0.02～0.04 的差距一般在误差范围内。本文不包含记忆原文、记忆 ID 或 key。

## 结论

- **重排（已上线，2026-10-19）**：回退链 Mac 上的 `BAAI/bge-reranker-v2-m3`（Apple 神经网络引擎，经 eeANE）→ Voyage `rerank-3-lite` → 本地 mmarco。Mac 在线时数据不出家门，每次约 2.3 秒；Mac 关机或离开局域网时约 3.5 秒后转给 Voyage。
- **嵌入（已上线，2026-10-19）**：从英文的 `bge-small-en-v1.5`（384 维）换成多语言的 `BAAI/bge-m3`（1024 维），在 LXC 的 CPU 上每次查询约 80 毫秒；中文查询的语义检索最差排名从第 92 名变为第 7 名。最大序列长度限制为 1024（见[已知问题](#已知问题与教训)）。
- **候选池**：`budget: low` 的重排候选上限设为 100（`HINDSIGHT_API_RERANKER_MAX_CANDIDATES_LOW`），所有自动召回都走这一档。
- **质量排序**（线上候选池、Hindsight 打分方式）：Voyage rerank-3-lite ≈ Voyage rerank-3 ≈ Cohere v4.0-pro ≥ bge-reranker-v2-m3 > Qwen3-Reranker-8B ≈ Jina v3 > mmarco > Cloudflare bge-reranker-base。前几名之间的差距不显著；直接答案进前 8 名的比例都是 100%，差别主要在第 1 名的准确度。

## 测试方法

- **质量**：nDCG@5（相关度 2 = 直接答案、1 = 相关、0 = 无关）、第 1 名命中、答案进前 8（客户端每次实际拿到 8～25 条）。按 Hindsight 的方式打分：分数超出 [0,1] 时先过 sigmoid，再乘时间、时间范围和证据三个加权系数。
- **延迟**：复用 HTTPS 连接，与 Hindsight 客户端一致。早期“每次新建连接”的测法会多算 0.5～1.5 秒，相应数据已重测。
- **客户端实际参数**（2026-10-19 核实）：Hermes 各 profile 和编码 agent 钩子都是 `types=[observation]`、`budget=low`、`max_tokens=2000`，每次返回 8～25 条；MCP 的 recall 工具默认 `budget=high`、全部类型、4096 token，只在 agent 主动调用时使用。

mmarco 作对比：i5-8500 CPU 约 3.2 s；换成 OpenVINO FP32 约 2.7 s，ONNX O3 约 3.0 s，INT8 没有收益；在 Mac GPU 上约 0.54 s。运行时不是 CPU 上的瓶颈，算力才是。

**神经网络引擎的要点**：
- macOS 27 起单个模型最大 1 GiB，bge-reranker-v2-m3 的 FP16 约 1.06 GiB；超限时系统不报错，直接退回 CPU。eeANE 把模型拆成两部分来解决。
- 一个模型包里放多种输入尺寸（EnumeratedShapes）时，Core ML 会拒绝使用神经网络引擎。eeANE 按每个序列长度单独编译一个模型。
- 输入尺寸必须预先固定，不能按实际长度动态变化。档位从 6 个细分到 7 个，差别小于测量波动；批大小 4 每条反而更慢，而且 eeANE 的 reranker 只支持批大小 1。
- 每个档位单独带一份权重（约 1.1 GB），上线保留 128/192/256/320/384/512 六档。

recall@50 三者（后两个）都是 1.00。云端的 voyage-4-lite 和 Cloudflare `@cf/baai/bge-m3` 质量与 bge-m3 相同，但嵌入要把每一条记忆都发出去，暴露面比重排大得多，没有采用。嵌入也不能放在 Mac 上：写入路径 7×24 运行，且不能用别的模型顶替（向量必须同源）。

上线后用线上 IaC 库的 22 条查询核对语义检索一路（只看嵌入）：中文中位排名 3 → 1、最差 92 → 7、进前 5 的 7/11 → 10/11；英文基本持平（有一条从第 4 降到第 10）。

## 已知问题与教训

- **litellm-sdk 重排不使用自己的超时设置**（Hindsight 0.10.2）：调用 `litellm.arerank` 时没有传 timeout，卡住时最长等 600 秒。用 litellm 的全局环境变量 `REQUEST_TIMEOUT` 限制；本机只有重排用 litellm。
- **bge-m3 默认最大长度 8192**：给 4 万～19 万字符的心智模型生成向量时，单进程用到 6～7.6 GB，导入在 LXC 的 8 GiB 上限被 OOM 杀掉（2026-10-19 21:49、22:06 AEDT，两次）。线上服务刷新心智模型时同样有风险。已在 `hf-cache` 里把 `sentence_bert_config.json` 的 `max_seq_length` 改为 1024。
- **导入会分配新的记忆 ID**，也不会恢复操作历史（审计日志、LLM 请求记录）。
- **按序号成员不继承主配置**：回退链里第 n 个成员的每项设置都要用 `_n_` 前缀单独写（例如 mmarco 的分桶批处理和并发）。
- **eeANE** 是 GPL-3.0 的个人项目（审阅过源码：只调用 `xcrun coremlcompiler` 和 `sysctl`，给本地目录时不联网）；必须配置至少一个嵌入模型才能启动；默认按需加载、空闲 5 分钟卸载，冷加载约 27 秒，所以重排模型设为常驻。
- **Mac 的私有 Wi-Fi 地址**：轮换或固定的随机地址都会让网关的静态分配失效，家里网络已改为使用硬件地址。

## 隐私与成本

- 重排：Mac 在线时数据不出局域网；Mac 不在时，每次约 100 条候选的原文发给 Voyage（美国）。Voyage 默认保存数据并可能用于训练，需要在控制台的 Terms of Service 里关闭（关闭后为零保留）。
- 嵌入：全部在 LXC 本地。
- 费用：Voyage 只在 Mac 不可用时产生，前 2 亿 token 免费。Mac 常驻约 0.5 GB 内存；LXC 内存由 4 GiB 调到 8 GiB。
