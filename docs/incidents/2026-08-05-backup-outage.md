## 1. 摘要

2026-08-05 例行核对备份状态时发现，PBS datastore 中**每个备份组只有一个快照，全部日期为 2026-01-31**——即 PBS 初始部署当天。此后 186 天，每日 02:00 的计划备份作业从未成功过一次，且**无人察觉**。

另有 3 个工作负载（107 jenkins、109 claude-agent、110 claude-desktop）**自创建起从未被纳入备份作业**，从无任何恢复点。

排查过程中另发现两起独立事故：Ansible 动态 inventory 于 2026-07-30 失效（见 3.4）、以及排查当晚一次由 IP 地址冲突引发的网络故障（见 3.5）。

**未发现生产数据丢失**——期间没有已知的、依赖该备份进行恢复的事件。但这只能说明没有触发损失，不能证明数据完好；**2 月至 7 月之间的历史恢复点已永久缺失，无法补回**。

### 1.1 事故状态：为何尚未关闭

2026-08-06 已为全部 10 个工作负载取得新的恢复点。但这只是**终止了 RPO 继续恶化**，不构成永久修复：

- 根因（备份计划与冷机电源策略不闭环）**未消除**
- T7910 已于 10:25 按用户要求再次关机，**下一次 02:00 作业将因完全相同的原因再次失败**
- 无告警、无覆盖面校验，**下一次失败仍然不会有人知道**
- 备份仅验证了「作业返回成功」，**未做任何恢复演练**

在 6.1 节 P0 项完成前，本事故应保持开启状态。

## 3. 根本原因

按性质分为四类。**3.1–3.3 共同导致了本次备份事故；3.4 与 3.5 是排查期间发现的关联事故**，与六个月备份失败无因果关系，仅因同期发现而一并记录。

> **表述约定**：本节区分「**已证实**」（有直接观测证据）、「**推断**」（由证据倒推，无直接观测）、「**待确认假说**」（尚缺关键证据）。

### 3.1 直接原因：备份计划与冷机电源策略不闭环

PBS 运行在 T7910 上，而 T7910 被定位为「冷备份服务器」，平时关机。备份作业**每日 02:00** 执行，打向一台通常关机的机器。

**这里的根因不应简化为「WOL 未实现」。**即便 WOL 完全实现，也不能解决问题——因为 [pbs-iscsi-veeam-guide.md](../archive/pbs-iscsi-veeam-guide.md) 第 4 节设计的唤醒频率是**每周六 00:00**：

> **每周六 00:00**: `pve0` (Cron) 发送 WOL 唤醒 T7910

而实际作业是**每日**执行（[pbs-client defaults](../../ansible/roles/pbs-client/defaults/main.yml)，`pbs_backup_schedule: "02:00"`）。**一周中仍有 6 天会失败。**真正的缺陷是备份计划与电源策略从未对齐，也从未有人验证二者是否闭环。

**已证实**——唤醒机制确实从未实现，在 pve0 上核查：

```
root crontab      : no crontab for root
/etc/cron.d       : e2scrub_all  vzdump  zfsutils-linux     ← 无 WOL 相关
systemd timers    : 全部为系统自带，无 WOL
WOL 工具          : wakeonlan / etherwake / ether-wake 均未安装
```

**证据链的一处倒置**：被引用的这份设计文档日期为 **2026-02-03，状态为「草案」**，晚于 1 月 31 日的 PBS 部署。因此它不是"一项被遗漏的既定控制"，而是**一份从未被验收落地的计划**。真正缺失的是**上线验收环节**——PBS 部署后没有任何检查确认"备份能否在目标关机的前提下按计划完成"。

**待确认**：「当前硬件无法实现 WOL」这一判断**已被推翻**。PCI 清单显示 T7910 有两个铜口：

```
0000:00:19.0  Intel I217-LM (板载千兆)
0000:05:00.0  Intel I210   (PCIe 千兆)
```

先前"仅有光口"的说法应为"仅有光口接线"。WOL 在接线后**很可能可行**（设计见 7.2）。

**未能证实的部分**：现有证据（8 月 5 日的配置核查 + 近期十余条 PVE 失败记录）**不足以证明整个 186 天都是同一原因**。期间是否存在人工开机、PBS 服务异常、ESXi 网络或存储问题导致的其他失败，缺少完整的 PVE 作业历史与 T7910 开关机记录来佐证。

### 3.2 覆盖面缺口：备份对象采用手工白名单，无任何漂移检测

**这是一个独立于 3.1 的失败模式**，即使 3.1 完全修复也不会消失。

`pbs_backup_vmids` 是一份**显式白名单**，由 `backup-jobs.yml` 拼接为 `--vmid 100,101,…`。新建 guest 时，系统中**没有任何环节**会察觉它、检查它是否在备份集内、或因此报错。

**后果**：107（2 月 3 日创建）与 109（3 月 30 日创建）分别沉默了约 6 个月与 4 个月，从无任何恢复点。

**这个缺口有两层防护都是空的：**

1. **无自动纳入**——白名单是"默认不备份"，漏做动作的后果是数据裸奔
2. **无覆盖面校验**——`setup-pbs-backup.yml` 的 verify play 只检查「存在一个指向 PBS 的作业」，**不检查作业包含哪些 VMID**。因此在 107/109/110 毫无备份的数月中，验证始终通过

**特别注意**：即使 6.1 节的备份失败告警建成，**也抓不到这个缺口**——作业从未尝试备份它们，不存在"失败"可上报。**静默的缺席不会触发任何基于失败的告警**，因此覆盖面校验必须是一道独立的防线。

### 3.3 未被发现的原因：没有主动通知，也没有备份新鲜度监控

这是 MTTD 接近 186 天的**直接原因**——它不会让备份更容易失败，但决定了失败会持续多久无人知晓。

系统中存在被动查看界面（PVE 任务历史、PBS task log，本次排查正是依赖它们），但**不存在**：

- 作业失败的主动通知（邮件 / webhook / 任何推送）
- 「最新成功快照年龄」的新鲜度监控
- 「作业根本没有运行」的 dead-man 告警
- 定期巡检的责任人与节奏

**一个没有主动告警的备份系统，在故障时与正常时表现完全一致**，直到需要恢复的那一刻才会暴露。

### 3.4 关联事故 A：Ansible 动态 inventory 失效

**引入时间：2026-07-30 13:42**

`ansible-core` 2.21 移除了 `get_bin_path()` 的 `required` 关键字参数：

```python
# ansible-core 2.21.2
get_bin_path(arg, opt_dirs=None)

# cloud.terraform 4.0.0 — plugins/inventory/terraform_provider.py:194
terraform_binary = process.get_bin_path("terraform", required=True)   # TypeError
```

**结构性成因是版本管理的不对称：**

| 位置 | 内容 | 后果 |
|---|---|---|
| `requirements.txt` | `ansible-core>=2.16` | 无上界，每次重建拉最新 |
| `ansible/requirements.yml` | 7 个 collection **全部无版本约束** | — |
| `.devcontainer/post-create.sh` | `pip install --upgrade --force-reinstall` | ansible-core **持续前进** |
| `.devcontainer/post-create.sh` | `ansible-galaxy collection install`（**无 `--upgrade`**） | collection **冻结在首次安装时（2026-02-10）** |

核心不断前进、集合原地不动，撞车是时间问题。

**后果**：所有以 `hosts: pve0` 为目标的 playbook 无法执行（`deploy-claude-agent.yml`、`setup-pbs-backup.yml`、`deploy-caddy.yml`、`update-ubuntu-template.yml`），因为 inventory 中不存在该主机。

**不应把它列为备份事故的贡献原因**：该故障 7 月 30 日才出现，此前 5 个月的无人察觉与它无关；也没有证据表明这期间存在会主动检查备份状态的 Ansible 任务。二者仅是同期存在，非因果。

**另需注意**：[CLAUDE.md](../../CLAUDE.md) 中「inventory 解析失败就先跑 `refresh-terraform-state.sh`」这条指引对此错误**无效**——它不是 state 不同步，而是版本不兼容。

**"静默"一词需修正**：`TypeError` 与 inventory parse warning 本身是可见的错误输出。真正的问题是**无人执行、也无人检查**这些 playbook，因此错误从未被读到。

**另一处归因错误（已修正）**：报告初稿推测重复定义来自 `terraform/proxmox` 的残留 state。经核查，实际是两个明确的定义源：

```yaml
# ansible/inventory/esxi/esxi_vms.yml   ← 静态定义
esxi_vms:
  hosts:
    llm-server:
```
加上 [terraform/esxi/llm-server.tf:56](../../terraform/esxi/llm-server.tf) 的 `ansible_host` 资源。删除其一即可，无需排查 state。

### 3.5 关联事故 B：IP 地址冲突（排查当晚）

2026-08-05 23:35:14，immich 已成功传输 43 分钟后突然中断，随后所有备份瞬间失败。

**已证实**：pve0 的 ARP 缓存中，192.168.1.249 指向了错误的 MAC。

| | MAC |
|---|---|
| PBS 真实 MAC | `00:50:56:8f:91:f2`（VMware OUI `00:50:56`） |
| 00:05 时 pve0 缓存的 MAC | **`98:b6:e9:02:57:11`** ← 非 VMware OUI |

**已证实**：执行 `ip neigh del` 清除条目后重新解析得到正确 MAC，8007 连续 10/10 成功。这是主动干预、可重复验证的强证据，足以证明**当时的连接失败由错误的 ARP 映射造成**。

**推断（无直接观测）**：23:35:14 的中断由同一机制引起。我们没有 `ip monitor neigh`、周期性邻居表采样或抓包，无法证明 ARP 条目恰在该时刻翻转——这是由"23:35 中断"和"00:05 查到错误条目"倒推的。

**证据强度较弱的几处，如实标注：**

- **22:46 的 ping 是否修复了故障**：仅有时间先后关系。按 RFC 826，主机收到 **ARP 报文**时才会用其中的 sender MAC 覆盖已有条目；**普通 ICMP/IP 报文本身不会更新 ARP 表**。因此可能的机制是：ping 促使 PBS 需要解析或重新验证 pve0，从而发出带 PBS sender IP/MAC 的 ARP 报文，pve0 据此覆盖了错误条目。**没有抓包，无法确认。**同样能解释恢复的还有：pve0 邻居状态机因发送失败自行进入 probe 重新 ARP、冲突设备短暂离线、两者竞争应答时恰由 PBS 胜出。
- **00:04:36 的 `Connection refused`**：只能证明某个终点返回了 TCP RST。归因于"冲突设备主动拒绝"是**推断**——中间设备的 `REJECT --reject-with tcp-reset` 或 PBS 本身同样可能产生 RST。确认需要当时的二层抓包。
- **"PBS 侧无异常，故数据包未到达 PBS"**：这是排除法。未重启、无 OOM、内存正常只能降低 PBS 本机故障的概率，不能正向证明虚拟交换机、物理链路或短时 service stall 不存在。
- **devcontainer 同时失联**：本可显著加强重复 IP 假说，但当时**未采集 devcontainer 侧的 `ip neigh` 与抓包**，这条佐证已无法补取。

**这也解释了 22:44 那次一度无法归因的失败**——PBS 当时已开机 5.5 小时、服务正常、8007 在监听，却报 `Connection timed out`。推断的完整链条：

```
22:44  ARP 指向冲突设备          → 失败                    【推断】
22:46  ping 触发 ARP 重新解析     → 覆盖为正确 MAC           【推断，机制存疑】
22:48  重试                      → 成功                    【已证实】
22:51  immich 开始传输            → 正常运行 43 分钟         【已证实】
23:35  ARP 再次翻转               → connection reset        【推断】
00:05  ip neigh del              → 恢复,10/10              【已证实】
```

**根本成因仍是待确认假说**：DHCP 地址池覆盖静态 IP `.249` 只是候选之一。同样能产生该现象的还有：另一台设备手工配置了 `.249`、陈旧的 DHCP lease、克隆虚机继承地址、错误的静态保留、proxy ARP。**必须先识别 `98:b6:e9:02:57:11` 对应的设备**，再核对其地址取得方式，才能确定修复措施。用户已关闭冲突设备，识别工作待完成。

## 7. 改进项细节

### 7.1 pve0 的 ARP sysctl 加固

pve0 有两个接口在同一个 `192.168.1.0/24` 网段（corosync 双环设计：ring0 = `.50`，ring1 = `.20`）。当前 sysctl 为默认值：

```
net.ipv4.conf.all.arp_announce = 0
net.ipv4.conf.all.arp_ignore   = 0
net.ipv4.conf.all.rp_filter    = 2
```

**`arp_announce`** 控制发出 ARP 请求时使用哪个源 IP：

| 值 | 行为 |
|---|---|
| 0（当前） | 使用出接口上的任意本地地址，**可能宣告属于另一网卡的 IP** |
| 1 | 尽量避免宣告不在目标子网内的地址 |
| **2** | 总是选择对目标最合适的本地地址，即出接口自身的主 IP |

**`arp_ignore`** 控制是否回应针对本机 IP 的 ARP 请求：

| 值 | 行为 |
|---|---|
| 0（当前） | **只要该 IP 属于本机就回应**，不论请求从哪个网卡进入 |
| **1** | 仅当被查询 IP 配置在收到请求的网卡上时才回应 |
| 2 | 在 1 基础上要求发送方同子网 |

在 0/0 默认值下，两个网卡都会应答针对 `.50` 和 `.20` 的 ARP，对端可能将任一 MAC 缓存给任一 IP（**ARP flux**），导致路径不确定。改为 `arp_announce=2` / `arp_ignore=1` 后每个网卡只为自身 IP 应答，路径确定，且**不影响 corosync 双环**——反而使每个 ring 的流量各走各的接口。

**`rp_filter`**（反向路径过滤，RFC 3704）：

| 值 | 行为 |
|---|---|
| 0 | 关闭 |
| 1 | **严格**：回程路由必须指向数据包进入的接口，否则丢弃——**会打断多宿主/非对称路径** |
| **2（当前）** | **宽松**：源地址只要经任意接口可达即接受 |

**`rp_filter=2` 是多宿主机的正确设置，保持不变，不要改为 1。**

**实施建议**：写入 `/etc/sysctl.d/`，不要只用 `sysctl -w`；这是生产集群节点上的在线网络变更，建议在可接触控制台时执行。

> **两点保留意见**：
>
> 1. **此项与本次事故根因无关。**排查中曾一度把 ARP flux 当作成因，后经证实错误——pve0 的铜口当时处于 `NO-CARRIER`，只有一个接口是活的，ARP flux 无从发生。真实成因是 3.5 节的 IP 冲突。此项纯属独立加固。
> 2. **「不影响 corosync 双环」不应作为既定事实。**内核文档指出 `arp_ignore`/`arp_announce` 的实际效果取决于 all/接口两级取值与真实入接口；在 bridge、VLAN、bond 场景下（本例 IP 配在 `vmbr*` 而非物理口），仅凭"两网卡同子网"不足以保证 `2/1` 无副作用。**实施前须在线验证** corosync 双环、集群通信与虚机网络均正常。

### 7.2 T7910 的 WOL 端口设计（L2-only，不配 IP）

**WOL 不需要 IP 地址。**magic packet 是二层以太帧（`FF:FF:FF:FF:FF:FF` + 目标 MAC 重复 16 次），由网卡固件在断电状态下做模式匹配，不经过 IP 协议栈。因此该端口不配 IP 既可行，也更安全——无攻击面，且不可能再产生 3.5 节那类 IP 冲突。

**选用板载 I217-LM（`0000:00:19.0`），不用 I210。**Dell 工作站 BIOS 的「Wake on LAN」选项通常只对板载网卡生效；插卡唤醒依赖「Power on by PCIe device」类选项，支持程度不一。

**ESXi 侧配置**：物理网卡（vmnic）本身不持有 IP，IP 只存在于 VMkernel 适配器上。因此"不配 IP"的做法是：

1. 新建一个**专用 vSwitch**（如 `vSwitchWOL`），把该 vmnic 作为唯一上行链路
2. **不在其上创建任何 VMkernel 适配器**，也不挂 VM 端口组

> 建议专用 vSwitch 而非并入现有 vSwitch：并入会使其成为管理网络的冗余上行，流量可能从该口发出，重新引入"同网段多接口"的路径不确定性。

**三个必须同时满足的条件**：

| 层面 | 设置 |
|---|---|
| BIOS | Power Management → **Wake on LAN → LAN Only**；若有 Deep Sleep Control 需**关闭**（深度睡眠会切断网卡供电） |
| ESXi | `esxcli network nic get -n vmnicX` 应显示 `Wake On Lan Supported: true` |
| 交换机 | 该口配为对应 VLAN 的 access 口，与 pve0 同一广播域 |

**发送端（pve0）**：magic packet 必须**广播**发送（`192.168.1.255`）。单播需要 ARP 解析，而目标关机时无法应答。

pve0 上 `wakeonlan` / `etherwake` 均未安装。考虑到 CLAUDE.md 的「未经许可不装包」规则，建议用零依赖的 Python 脚本，由 Ansible 分发：

```python
# /usr/local/bin/wol.py
import socket, sys
mac = sys.argv[1].replace(':', '').replace('-', '')
pkt = bytes.fromhex('FF' * 12 + mac * 16)
s = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
s.setsockopt(socket.SOL_SOCKET, socket.SO_BROADCAST, 1)
s.sendto(pkt, ('192.168.1.255', 9))
```

**待补**：接线后需记录 I217-LM 的 MAC 地址并写入 Ansible 变量——magic packet 的目标是 MAC 而非 IP。

**注**：T7910 为 Xeon E5 v3/v4 + C610 平台，**不具备 vPro/AMT**（该特性属桌面/移动 Core 平台）。WOL 是唯一的远程开机手段。

### 7.3 告警设计（P0-2）

**单一的"作业失败通知"不足以覆盖本次事故的失败模式**，必须分层：

| 层 | 检测什么 | 为何必需 |
|---|---|---|
| **作业结果通知** | vzdump / PBS 作业失败 | 基础层 |
| **备份新鲜度监控** | 每个预期 VMID 的**最新成功快照年龄**超阈值 | 覆盖"作业跑了但某台失败"的情况 |
| **dead-man 告警** | 作业**根本没有运行** | 本次事故的关键——目标关机时作业可能连任务记录都不产生 |
| **通道自检** | 定期发送测试告警并确认送达 | 告警系统自身失效时无人知晓 |

**两条硬性约束：**

- **告警发送端不能是 PBS 自己。**PBS 随 T7910 关机，无法为"自己不在线"发出告警。发送端应在 pve0 或独立常开设备上。
- **被动仪表盘不算告警。**六个月无人察觉恰恰证明"可以查看"不等于"会被查看"。必须是推送式，且有明确接收人。

### 7.4 备份覆盖面校验设计（P0-3）

针对 3.2 节的缺口，两种修法，建议同时采用：

**方案 A：把白名单反转为黑名单**

```yaml
pbs_backup_exclude_vmids:
  - 108   # veeam-worker，Veeam 插件托管
  - 9000  # 模板，可重建
```

作业改用 PVE 全量模式加排除（`--all 1 --exclude ...`）。**默认包含**后，漏做动作的后果从"某台机器裸奔"变成"备份了不必备的东西"——代价从数据变成磁盘。**失败方向由危险翻转为安全。**

**方案 B：漂移检测**

```
未覆盖 guest = (集群实时 guest 集合) − (作业 vmid 集合) − (显式豁免清单)
若非空 → 验证失败 / 告警
```

现有 [setup-pbs-backup.yml](../../ansible/playbooks/setup-pbs-backup.yml) 的 verify play 只检查「存在一个指向 PBS 的作业」，需扩展为校验 VMID 集合。

**一般原则**：对安全关键的覆盖面，默认应为"包含"，排除必须显式且经过审阅。白名单静默地覆盖不足，黑名单覆盖过度；覆盖过度花的是磁盘，覆盖不足丢的是数据。

## 8. 经验教训

1. **没有告警的备份系统等于没有备份系统。**故障时与正常时表现完全一致，直到需要恢复才暴露。这是本次事故最应吸取的一条。

2. **设计文档写了但未实现的内容，比没写更危险。**WOL 唤醒机制被写进一份**草案**，此后所有人（包括本次排查初期）都默认它已存在。文档必须区分「已实现」「已验收」「仅为计划」，并在部署时留下验收记录。

2b. **两个组件各自"正确"，组合起来仍可能是错的。**备份计划（每日）与电源计划（每周）单独看都合理，闭环却不成立。**检查项应针对端到端结果**（"备份能否按 RPO 完成"），而不是各组件是否按各自设计工作。

2c. **静默的缺席不会触发基于失败的告警。**107/109/110 从未被纳入作业，因此永远不会产生失败记录。覆盖面校验必须独立于结果告警存在。

3. **未锁版本的依赖会静默漂移。**`ansible-core>=2.16` 这样的写法在环境重建时必然引入不可控变化，而 pip 与 galaxy 的升级行为不对称，使问题更隐蔽。

4. **只记录「怎么做」而不记录「为什么」的规范，会迫使后人从零考古。**这正是新规范文档设立「关键决策记录」与「被否决方案」两节的原因。

5. **静态 IP 必须从 DHCP 池中排除。**否则冲突只是时间问题，且症状具有迷惑性——本次故障中所有诊断都指向 PBS，而 PBS 完全正常。

6. **排查中要区分「已证实」与「假设」。**本次排查中曾基于单次样本提出 ARP flux 假说并表述得过于肯定，后被证伪。结论应随证据修正，并明确标注置信度。

7. **证伪一个「归因」不等于证伪整个「方向」。**排查早期曾怀疑 ARP，后因查明 corosync 为双环设计、且 pve0 铜口处于 `NO-CARRIER`（只有单个接口存活，ARP flux 无从发生）而否定了该方向。否定的理由本身成立，但被错误地从「ARP flux 不成立」推广为「ARP 不是问题」——而真正的机制**恰恰发生在 ARP 层**，只是成因是重复 IP 而非多接口。方向正确、归因错误时，应当只丢弃归因。

8. **排查动作可能改变现场。**从 PBS 侧发起的 ping 很可能覆盖了 pve0 的错误 ARP 条目，使故障看似"自行恢复"，一度误导了对故障持续性的判断。诊断时应记录每一步操作，并在解读"恢复"时先排除是否为自身操作所致。**更关键的是：错过的现场证据无法补取**——当时未采集 devcontainer 侧的 ARP 表与抓包，这条能显著加强重复 IP 假说的佐证已永久缺失。

9. **恢复不等于关闭。**取得新恢复点只终止了 RPO 恶化；根因未消除、未做恢复验证之前，事故仍处于开启状态。本报告初稿曾表述为「六个月缺口闭合」，属概念错误——历史恢复点无法补回。
