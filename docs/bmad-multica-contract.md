# BMAD × Multica 执行合同

版本：v4 修订 7.3。更新：2026-09-16。适用团队：唯一的 `BMAD Team`。

这是**在 Multica 上运行 BMAD 的执行政策**：授权、派工、交接、Issue 状态与失败处理。它不是第二套 BMAD 方法论；工作流顺序以本地原生导航及已启动工作流为准。

**跨模型评审不在本文件。** 那套能力是宿主无关的，见另一个包：

- `docs/bmad-cross-model-review.md` —— CR-1 协议、环境变量、边界声明、预检、冒烟、账单对账
- `docs/bmad-review-routing.md` —— 哪些 reviewer 走 Claude、哪些保留原生

本合同只在需要时引用它们，不复述其规则。换掉 Multica 时，那两份文档和六个 TOML 原样可用；要重写的是本文件和 `docs/multica-team.md`。

## C1. 规则来源与职责

读取项目 `AGENTS.md`、适用目录规则及本合同。已获授权的项目规则比本方案的建议更具体时，遵循更具体的规则；有冲突先报告，不擅自解除限制。

BMAD 的实际步骤、分支、交互检查点和完成条件决定流程；Coordinator 是其调度适配器，Multica 把已确定的工作分派给 Profile。不得把"想法→John→Winston→Amelia"写成必经流程，不另造状态机、步骤表或验收门禁。

正式业务 persona 加载项目实际安装的版本。Coordinator 不扮演产品经理或架构师，也不独立判断测试是否充分。共享本合同不会把新进程变成同一会话；每次任务仍须显式交接输入。

不另启一个同时选择同一 backlog 的外层循环。不按阶段拆 Squad，不按 reviewer 层或每个 BMAD 内部步骤创建 Issue；专家连续工作复用同一子项。

项目 Skill 由实际 runtime 按其原生目录发现，本包 Codex 角色默认使用 .agents/skills；其他工具使用对应项目适配目录。Workspace 绑定与运行时继承不是项目安装的替代。保持当前项目的 BMAD 版本和覆盖为权威，不为菜单显示复制同名 Workspace BMAD。

先使用任务已经指定的项目资源定位实际资料；临时 workdir 为空时继续按资源路径查找，不让用户重复提供目录。确认相关 Skill、配置与输入确实可读，目录扫描不冒充宿主 active 清单。正常反馈优先业务进展；路径、hash、模型证据仅在影响问题时简要说明。

## C2. 授权、范围与写入

只执行授权范围内的一项工作。已有授权覆盖当前任务时不重复索要；需要新增产品行为、改变批准接口、加入基础设施或处理高风险事项时，停止受影响部分并报告待决事项。

采用满足验收要求的最小充分实现，不主动扩展功能、抽象层或无关重构。不得削弱验收、删除有效测试、伪造测试结果来消除审核发现。

业务代码默认由 Amelia 写入。研究、产品、架构与 UX 成员只写其负责的获准产物；QA 只写测试与已允许的测试夹具/配置，Claude reviewer 只读。

同一子 Issue/工作项的写入串行执行。不同子 Issue 的依赖已满足、范围不冲突且公共接口已确定时，可在各自隔离 worktree 并行；允许同一个 Amelia Profile 同时执行多项，实际数量受 Agent 与机器并发上限约束。本包默认 Amelia=6、其他五个 Profile=1。不得并发改写同一公共文件或共享 BMAD 状态；共享测试端口、数据库、外部服务需先分隔或安排单写入者。

审核期间冻结该项所审工作区及输入；其他任务不能写入该工作区，独立模块在自身目录的工作可继续。有人正在修改或 Git 状态与交接不符时，不 reset、stash、覆盖、清理或删文件。跨模块集成只对明确版本执行，并完成相应集成验证。

不在 main 上开发或直接提交。本地提交、推送、合并、部署是不同授权：现行项目政策决定本地提交；推送、合并、生产变更和额外外发数据需要明确授权。若 Build Auto/Multica 默认自动提交与政策冲突，预检不通过，不以提示词代替解决冲突。

## C3. 导航、派工与交接

启动或接回时，Coordinator 对照父目标和当前授权，读取原生产物与会话记录，定位 workflow、意图/模式、当前步骤或章节；实际读取该项目的 SKILL.md 及当前步骤要求的参考文件，按其恢复方式继续。下一步已明确且获授权时按原生条件执行，不每步重复导航，不以角色名称、文件存在、完成通知或记忆代替步骤依据。不假定每个 Skill 都有编号步骤，也不要求用户提供新格式的状态表。

workflow、恢复位置、下一步或未决项对当前交付的影响不明确时，实际执行项目安装的 bmad-help：读取它的 SKILL.md，并按要求读取目录、解析配置、检查产物与完成证据。只提到名称或扫描文件不算执行；不要求它存在同名 shell 命令。导航不可用时报告缺口，不模拟结果或顺便安装/升级 BMAD。导航建议不等于新授权，可选项不变成必经门禁。

**多个必选后续交人判断。** bmad-help 给出多个必选下一步且原生没有唯一顺序/分支时，暂停受影响的派工，列出每项用途、前提/依赖、建议及待决定的顺序/分支/范围，请人类选择；不得自行挑一个、全派发或默认并行。全部必选时，排序选择不意味着可放弃其余项。原生已有明确先后关系时照做，不重复询问。

**人类介入与恢复。** 原生步骤要求选择/确认/验收、范围或已定决策冲突、下一动作超授权、导航后仍有歧义、必需能力/环境不可用且需选择恢复或替代方案、原生指令冲突或无进展循环，均由负责者说明当前步骤、事实/尝试、影响、具体问题与建议并等待决定。技术分析由专家做，Coordinator 不代替用户裁决。专家正常问答留在子项；跨角色、范围、授权问题由 Coordinator 协调。只暂停受影响工作，独立且获授权的工作继续；正常等待用户不自动 Blocked。已有明确恢复条件的外部阻塞不反复追问。回答写回原生记录后从暂停处恢复，不初始化新流程或扩大授权。Cancelled 不算成功；用户取消/拒绝的任务不自动重开、重派或改建新子项绕过；原因不明先查，仍有歧义就问人。

每轮在原 Issue 简短说明所依据的原生文件/章节、相关产物和决定（派工、等待具体决定/条件或交付验收）；这些是已有流程证据，不新增交接格式或状态数据库。

Multica 的 Squad 创建页只配置名称、描述、Leader 和成员；它不承载 Skills、Runtime、Model、Thinking 或 Speed。Profile 的 Instructions 承载长期职责边界，Profile 的 Execution 设置承载模型、推理、速度、访问和并发；每次 Run 再决定实际调用的 workflow。不能以 Squad 名称、Description 或成员关系推断任何 Skill 已绑定。

`docs/multica-team.md` 的映射只决定已经选中的工作流由谁执行，不决定工作流先后。未知 Skill/多义映射交人确认，不模糊匹配到"最像"的人。

成员执行一次已派工作后在实际执行该项的 Issue 回报，不自行 @ 下一成员。Coordinator 使用平台 roster 的真实成员 ID/mention 派工并结束当前 Run，不在父 Run 中轮询等待。

**评论按真实收件人路由。** 服务端优先处理明确的 Agent/Squad mention；没有这类 mention 而只有人类成员 mention 时不触发 Agent。因此当前阶段仍在讨论、解释或等待用户补充确认、且不需要调度时，业务成员在评论正文用真实的人类 mention 定向给需要回答的人，不混入 Agent/Squad mention、不用 @all；正式阶段交付、需要换角色/重派工、或阻塞依赖链需要协调时，仍显式交回 Squad/Coordinator 并附产物与下一步。不能用人类定向评论隐藏必需的交接。该规则必须写进每个成员 Profile 的 Instructions——只写在 Squad Instructions 里不生效，因为那只注入 Leader。

已获准实施且原生流程明确的独立模块使用带父子关联的不同子 Issue；先查看已有子项并复用，写明范围、验收条件、修改路径、依赖、输入版本和完整 Skill ID，再启动。澄清/拆分是否必要由原生步骤或导航判断，再映射对应专家，不额外插入前置阶段。多个 ready 子项的顺序或并行已经明确时，可按实际容量同时交 Amelia；此规则不授权自行裁决多个必选后续。读取并发与跨项目占用；不可见时由平台队列限流，不猜测容量或自行调高设置。

**持续讨论使用专家子 Issue。** 父 Issue 保持 BMAD Team；Coordinator 按工作范围查重后创建/复用同 Project 的子项，明确 Skill、模式、断点、可读输入版本及验收，直接指派专家，仅触发一次，不在子项代发聊天根评论。专家在子项直接与用户讨论，不重启原生工作流。评论触发的 Run 必须回复本轮触发或合并进本轮的评论，不能省略 --parent 强建顶层，也不能固定为旧根 ID；指派触发且无触发评论时正常发布首条。用户在子项直接回复，预览应只启动专家。旧历史和草稿保留，跨 Issue 资料通过明确版本/附件交接，不假定文件或会话自动共享。

**子项完成再接回。** 子项交付在本项记录产物、版本、未决事项和检查结果，只 @用户并进入 In Review 等验收；未经授权不得自行 Done。获准 Done 后通过平台原生子项/阶段完成事件唤醒父 Coordinator，不再额外 @一次完成。Run completed、In Review 与等待用户不是终态；Cancelled 会满足平台终态计数但不能当成功。stage 是同批屏障；未设 stage 的子项也作为一批全部终态后通知。Coordinator 接回后核对结果和授权，再按 BMAD 原生导航决定继续、换角色或等待，不预建固定流水线。需协调的 Blocked 或重派工可在父项明确 @Coordinator 报告一次；不把失败隐藏到验收之后。此前通用交接规则在子项正常验收路径上以本条原生完成通知为准。

创建子 Issue 前先读一次已有子项；两个协调回合可能同时发现"尚无子项"。发现重复创建时保留先建的一项，关闭后建的并注明重复。

每个子项只选指派或真实 mention 中的一种触发方式；指派已有 Run 就不重复 mention。去重按同一子 Issue、执行者和工作范围判断，覆盖排队、准备、运行及正常等待用户回答；父 Issue 有活动 Run 不是暂停所有独立子项的理由。进度不算完成，容量满则等待后续完成/状态事件重新核对，不在一个 Run 中循环等待。

依赖项必须交付下游可访问的分支/commit、产物路径和验证结果；下游显式取得该版本，不能假定另一个 worktree 的修改自动可见。只等待真实依赖，无关子项仍可推进。**审核与交付必须指向同一版本**：记录送审的 commit/tree 和最终交付的 commit/tree，两者不一致时重新审核。工作树有未提交改动时，先固定快照再送审。

`bmad-build-auto` 仅在明确选择且原生入口能限定不同工作项、独立工作目录与状态时并行；否则串行运行该循环，禁止多个实例自主挑选同一 backlog。

Coordinator 将子项结果与未决项放回原生步骤并对照父目标；原生流程或父项验收确需跨模块集成时，才给 Amelia 派对应版本的集成验证，不把它作为所有讨论/文档任务的固定阶段。父目标和本项原生完成条件的证据均满足才进入 In Review；不独立裁定测试充分，不自动合并主分支或部署。详细派工例子见团队文件 T3.1。

业务产物与 BMAD 状态保留在原生文件中；派工、批准和运行关联保留在 Issue；代码与测试关联实际版本。不建立第三套状态数据库。

普通回报说明已有进展、对应文档/会话记录、当前未决问题及下一步。派工评论补充完整 Skill ID、原生模式和输入位置即可，不新增 handoff 文件或要求用户填表。只有审核/实现验收才附相应版本、模型、费用及测试证据。正常交互不转成一份通用入口审计报告。

## C4. 跨模型审核在本团队的落点

规则本身在 `docs/bmad-cross-model-review.md` 和 `docs/bmad-review-routing.md`。本节只说它在 Multica 上怎么落地。

实现使用已批准的 OpenAI 模型；指定审核层/lens 由 CR-1 启动独立 Claude 进程执行。Claude 只出报告，宿主保留原工作流的汇总与分诊。拒绝有效 findings 需证据；产品/架构分歧升级，不由轻量 Coordinator 裁决。

CR-1 需要的环境变量必须进入**实际执行 Run 的 Profile Environment**——终端 `export` 不会进入已启动的 daemon。哪些 Profile 需要：执行 Build Auto / Code Review / Architecture / Review 的成员（实际上就是 Amelia、Winston，以及作为 review 宿主的产物负责人）。Coordinator 不需要。

某项审核因缺配置、方法文件或认证而未运行时，按 routing R1.5 记为"未执行"并保留在回报、交接与 Issue 中。部分失败不毁掉整轮工作，但**存在未执行的必需审核时，父 Issue 不得进入 In Review**。回报区分"已审核""零发现""未执行"三种状态。

评审触发、必需 reviewer、发现分诊、修复、复核和结束条件遵循当前项目实际安装的 BMAD 原生工作流。适配层不规定额外复核轮数，不设置“初审→复核→最终复核”的固定循环；原生未要求的额外调用不能冒称原生必需。原生未明确的地方如实说明，由宿主依据实际发现和用户授权判断，不把可选复核变成验收门禁。原生 architecture Update 本身要求 Reviewer Gate，不能以本条为由跳过；普通问答或记录信息也不因一个 Multica Run 结束就自动视为完成一次 Update/Finalize。CR-1 只替换选定 reviewer 的执行通道，不改变其方法或报告语义。

`bmad-build` 的审核层默认关闭；派工要跨模型审核时在任务中明确写出。未列入 routing R0 的入口不在覆盖保证内。

## C5. QA 的执行范围与失败路径

只有存在明确补测试任务、规划中的额外 API/E2E 要求或仍未补齐的覆盖缺口时才执行 QA；必需的实现测试不能推迟给 QA。覆盖要求由需求、工程判断和审核证据确定，不由 Coordinator 自行猜测。

QA 在新任务上下文中加载既有目标版本、验收条件、覆盖范围、测试环境、允许修改的测试路径。复用已有框架；没有框架先报告选择，不自行增加依赖。不得修改业务代码/Spec/验收条件或弱化断言。

测试代码错误可在允许范围内修正；真实产品缺陷报告最小复现并回交；环境缺失、权限不足、未运行分别如实报告。不能等 `on_complete` 才处理失败，因为失败路径可能根本不会触发它。保留实际退出码、通过/失败/跳过/未运行情况，不把"生成了测试"写成"已验证"。

并行 QA 必须在启动前取得每 Run 独占的 summary/输出路径；做不到就串行执行 QA，不要靠"事后复制"抢救共享路径——后写的 Run 会覆盖先写的证据。

## C6. Issue 状态与恢复

按平台原生状态语义管理当前 Issue：开始处理后保持 In Progress；进入 In Review 前，同时对照父目标和本项适用的 BMAD 原生完成条件，给出实际完成证据及剩余事项不影响本项验收的依据。现有子项全 Done、Run completed、审核次数或文件状态都不能替代判断；draft/未决项与完成结论矛盾时核对其真实影响，不能把未完成设计笼统改称“实施前门槛”。仍有本范围内获授权工作就继续，需人决定就具体询问；真正完成后停止派工，不制造泛泛整理任务。Done 由人/已授权集成完成。研究/规划验收产物本身，功能任务不能在规划完成时宣布交付。

BMAD 的 `ready-for-dev` 不是授权，`in-review` 不是整条 Issue 等人工验收，`done` 不是用户已接受。内部状态和恢复分支完全交给原生 workflow；Coordinator 不手改状态解锁、不把 done 当成默认重跑理由。

规划中的正常提问应清楚说明等待用户回答，保持已有工作流与记录；不将其记为技术执行失败，不因单次 Run 结束宣布整个方案完成。

重复通知按子 Issue、执行者、工作单位、Skill、输入版本和活动 Run 去重。等待批准/环境恢复时记录恢复条件，不无限重试。已有 blocked 执行由原生恢复指引处理，必要时专家重新规划；保留历史证据。某一子项受阻时记录受影响依赖链，其他独立子项继续；父 Issue 不因一个子 Run 完成或阻塞就机械改为 Done 或 Blocked。

## C7. 暂停、回滚与恢复

审核通道自身的故障处置见 `docs/bmad-cross-model-review.md` X9。本节是团队层面的动作。

1. **冻结派工，不删除证据。** 记录 Issue/Run、输入与代码快照、有效配置、模型/费用、失败日志；活动 Run 要么完成，要么由获授权人明确取消。停派工不等于自动杀死运行。
2. **选择恢复方案。** 优先恢复上一组端到端验收过的配置与 CLI/Skill 版本。没有可用基线时继续阻塞，或由你明确批准人工 Claude 审核、临时同模型审核等替代路径，并记录范围、期限及尚未满足的 cross-model 要求。
3. **精确回滚配置文件。** 在没有活动写入且获授权后，从备份恢复受影响的文件，重跑核心文档 X6 预检。不得直接删除 QA 的 TOML：测试写入与失败边界不能随审核通道一起撤销。不使用全仓库 reset、clean，不覆盖业务改动或人工未提交文件。
4. **逐项恢复工作。** 按原生 blocked/done 等恢复语义继续或建立关联的新执行；不手改旧状态制造成功，不把回滚同模型结果标成 Claude 审核通过。取得相应新增证据后才进 In Review。

本节是治理与恢复规则，不是自动执行脚本；删除配置或接受风险均须实际授权。跨模型故障本身不能授权降低验收标准。
